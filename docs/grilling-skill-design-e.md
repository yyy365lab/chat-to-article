# AIに自分を問い詰めさせてからスキルを作ったら、着手前に設計が3回変わった

**TL;DR**
1. チャットを記事にするスキル `chat-to-article` を作った。SKILL.md 1枚・約4,000字、スクリプトなし。
2. 実装前に grilling(AIに容赦なく質問させる工程)を5ラウンド回したら、1行も書かないうちに設計が3回ひっくり返った。
3. 効いたのは「事実はAIが調べ、決定は人がする」という線引き。実測値が出た瞬間に設計が書き換わった。

## 作ったのは、チャットを記事に変えるスキル

`/chat-to-article` と打つと、AIが会話から「何をやったか」の目次を内部で作り、5問だけ聞いてくる。何の話にするか / 読者は誰か / 主眼は / 公開範囲は / 文体は。全部に推奨案が付くので、返事は「全部推奨で」の一言で済む。この記事もその一言から出てきたもの。

実体は SKILL.md 1ファイルだけ。スクリプトも外部参照もない。理由は配布物だから。Gemini のようにプロンプト1本しか登録できない環境でも、貼れば同じ挙動になる形にしたかった。💡

## grilling は「いま聞ける質問」しか出さない

元ネタは Matt Pocock のスキル集(37個)にある `grilling`。本体はたった 2,015バイト。

> 決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

普通のAIも確認の質問を並べる。でもその中に「上の答え次第で消える質問」が混ざっていて、答える側が混乱する。grilling はそれを構造的に禁じ、依存する質問は次のラウンドへ送る。だから1ラウンドが短く、答えやすい。

## 着手前に3回、設計が崩れた

| 何が崩れたか | きっかけ |
|---|---|
| 記事の仕様を作りかけていた | 「私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。」——読者や公開先は記事ごとに変わる項目。スキルに焼き付けるべきは答えではなく、聞く仕組みだった |
| 過去ログ全部を素材にする案 | AIが勝手に実測した。A=9セッション34MB、B=1セッション15MB、C=0本。文脈に入らないし、ログが残っていない案件もある |
| スクリプト前提の設計 | 配布先に Gemini が含まれると分かった時点で、スクリプトもファイル読み取りも使えない |

2番目は、聞かれても答えられなかった。**事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない**——この一文が実際に効いた場面。決めるのは自分、調べるのはAI。

## 使ってみたら、初回の記事が要件定義書みたいだった

ドッグフーディングで1本書かせたら、仕様どおりに動いた。ただし文章が固い。名詞ラベルの見出し、体言止めの連打、「〜を実現した」。人が書いたブログに見えない。

そこで SKILL.md に文体の節と、文体プリセット6種(ゆるっと / ていねい / きっちり / 実況 / さくっと / ハンズオン)を足し、質問を4問から5問に増やした。この記事は「さくっと」で出力したもの。1本使ってみないと、この欠陥には気づけなかった。

## 真似するなら、最初の1回を必ず使ってみる

自作スキルは9個目、うち7個はスクリプトなしの Markdown だけ。作るのは難しくない。難しいのは、作る前に何を決めるかを決めること。そこを grilling に任せると、手戻りが質問の段階で潰れる。

設計から実装完了までの記録は1時間24分。そのほとんどは5ラウンドの問い詰めで、実装は終盤のごく一部。逆に言えば、**時間の使い先が変わっただけ**。

同じように自作スキルを育てている方、初回の出力で何がズレましたか。うまくいかなかった例のほうが知りたいです。🔥
