# AIに自分を問い詰めさせてからスキルを作ったら、着手前に設計が3回変わった

AIとのチャットを素材にして記事を書き起こすエージェントスキル `chat-to-article` を作った。実体は Markdown 1枚で、コードは1行も書いていない。だが今回書き残したいのは中身よりも作り方のほうだ。実装に入る前に「grilling(問い詰め)」という工程を挟んだところ、1文字も書かないうちに設計が3回崩れた。普通に「記事化スキルを作って」と頼んでいたら、この3つは全部、作り終えたあとに判明していたはずだ。

自分がスキルを作りたくなった動機は単純で、作ったものをコミュニティに共有したいのに、記事を書くのが面倒だったからだ。素材はチャットにもう残っている。ならばそこから起こせばいい、と考えた。

## 完成したのは、5問答えるだけで記事が出てくる Markdown 1枚だった

`chat-to-article` は明示呼び出し専用のスキルで、`/chat-to-article` と打つと起動する。まず会話から「何をやったか」の目次を内部で組み立て、そのうえで質問を5つ投げてくる。

| # | 聞かれること | 選択肢の例 |
|---|---|---|
| Q1 | 何を作った話にするか | AIが推測した一行を提示してくる |
| Q2 | 読者は誰か | 一般の開発者 / 特定コミュニティ / 社内 |
| Q3 | 記事の主眼 | 成果物の紹介 / 詰まった所と解決 / 得られた学び |
| Q4 | 公開範囲 | 一般公開 / 限定公開 / 社内のみ |
| Q5 | 文体 | 6種のプリセットから選ぶ |

要点は、全問に推奨案が付いていることだ。だから「全部推奨で」の一言で執筆が始まる。この記事もその一言から生まれている。Q4 は公開範囲を聞いているように見えて、実際には伏せ字の強度を決めるスイッチになっている。一般公開を選ぶと、個人名・社名・テナント名・絶対パスのユーザー名・トークンの類が既定で伏せられる。しかも置換した一覧は記事本文に書かず、チャット側で報告する。「※社名は伏せました」と本文に書いてしまうと、伏せたという事実そのものが情報になるからだ。

記事の構成は背骨が1本だけある。タイトル、書き出し、何ができたか、どう作ったか、分かったこと、結び。Q3 の主眼によって、そのどこを厚くするかだけが変わる。型を3つ用意する案もあったが、保守が3倍になるうえ、実際の記事はたいてい中間的なものになる。重心の指定だけで足りると判断した。

ファイルは `SKILL.md` 1枚、4,000字ほど。スクリプトも外部参照ファイルもない。この構成には理由があるのだが、それは後述ではなく、次の節でそのまま出てくる。

## grilling は「今聞ける質問」だけを出してくる仕組みだった

きっかけは Matt Pocock の [mattpocock/skills](https://github.com/mattpocock/skills) を眺めていたことだった。37個のスキルが入っている中で、作者が「最も人気があり、変更を加えるときは毎回使え」と書いているのが grilling だ。本体は 2,015バイトしかない。原稿用紙2枚ちょっとでこの評価なのだから、密度が高い。

中核はこれだ。

> 決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

普通のAIも「確認させてください」と質問を並べてくる。だがその中には、上の質問の答え次第で消滅する質問が平気で混ざっている。答える側は、まだ決まっていない前提を頭の中で仮置きしながら答えることになって混乱する。grilling はそれを構造的に禁じ、他の未解決の質問に依存する問いは次のラウンドへ回す。

もうひとつ、役割分担がはっきり書かれているのが効いた。

> 事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

事実はAIが調べる、決定は人間がする。この線引きが、あとで効いてくる。

## 崩壊1 — 「作りたいのは記事ではなく、スキルだ」

ラウンド2で、AIは素材の絞り込み方や公開先を聞いてきた。「どのコミュニティに出しますか」。もっともらしい質問だし、私は普通に答えかけた。ところが答えを書きながら妙な引っかかりがあった。これは今決めることなのか。止めてこう打った。

> 私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

これが一番大きな崩壊だった。決めるべきことが2層に分かれていたのだ。

| 層 | 内容 | いつ決まるか |
|---|---|---|
| A: スキルの仕様 | 発動方法、素材の取り方、出力先、伏せ字の仕組み | 設計の今 |
| B: 記事ごとの選択 | 読者、記事の単位、文体、公開先 | スキルが実行時に聞く |

読者も公開先も層Bだ。スキルに焼き付けるべきは答えではなく「聞く仕組み」だった。気づかずに進んでいたら、私の想定読者と私の投稿先が固定された、自分にしか使えないスキルが出来上がっていた。配布物としては欠陥品だ。

ここは正直、AIを責める気になれなかった。私の最初の依頼が「記事化するスキルを作りたい」という一文だけで、どちらの層の話をしているかを言っていなかったからだ。むしろ、質問攻めにされなければ、このズレは実装後まで表に出なかった。

## 崩壊2 — 素材にするつもりだった過去ログが、実測 34MB だった

「プロジェクト全体の会話ログを素材にする」と決めた直後、AIが勝手に実測してきた。頼んでいない。

| プロジェクト | セッション数 | 合計 |
|---|---|---|
| A | 9 | 34 MB |
| B | 1 | 15 MB |
| C | 0 | — |

34MB は文脈に入る量ではない。しかも C のように、ログが1本も残っていないプロジェクトもあった。別の場所で作業したものだ。

ここで効いたのが、さきほどの「事実を見つけるのはAIの仕事」だった。私は「プロジェクト全体を素材に」と発想しただけで、それが物理的に何MBになるかを知らなかった。聞かれていたら答えられなかった質問だ。同じ立場の方に伝えたいのはここで、AIに確認させるときは、決定を仰ぐ質問と、勝手に調べさせる事実とを分けたほうがいい。分けないと、答えられない質問を突きつけられて設計が止まる。

## 崩壊3 — 「Gemini ではプロンプトしか登録できない」で前提が消えた

3つ目は私の側から出した制約だった。このスキルは配布物にするつもりで、Claude Code だけでなく Gemini でも同じ挙動にしたい。ところが Gemini でスキル化するとプロンプト文しか登録できない。

この一言で、それまで積み上げた前提がまとめて崩れた。

- スクリプトが持てない。34MB を機械的に処理する案は消える
- ファイルが読めない。過去のセッションログという素材そのものが存在しない
- `references/` に分割しても読まれない。1枚に収めるしかない

面白かったのは、ここで問題の形が反転したことだ。34MB 問題は「Claude Code のときだけ起きる問題」であって、Gemini では逆に「素材が目の前の会話しかない」という真逆の問題になる。

そこで、処理手順は共通にして、素材の在り処だけを環境依存にした。上から順に、使えるものを使う。1に今の会話、2にユーザーが貼ったログ、3に読める環境でだけ過去のセッションログ。肝は1だけでも成立させることだ。長いチャット1本で作りきったプロジェクトなら、その会話が全体像そのものである。だからスキル本文には「素材が今の会話だけでも、謝らない・断らない」と明記した。AIは素材が薄いと言い訳から入りたがるので、そこを先に潰しておく必要があった。

## 使ってみたら、出てきた記事が要件定義書みたいだった

設計から実装完了までの記録は1時間24分。そのほとんどは grilling の5ラウンドで、実装は終盤のごく一部だ。作り終えてすぐ、この会話自体を素材にスキルを回してみた。作ったスキルを自分に向けるのだから、ドッグフーディングとしては理想的だ。

仕様どおりには動いた。質問は推奨案つきで出たし、会話の時系列をなぞらずに「3回の設計崩壊」という軸で再構成してきたし、伏せ字も効いた。ところが出てきた原稿を読んで、私は手が止まった。正しいのだが、面白くない。「〜を実現した」「〜が可能となる」が並ぶ、要件定義書のような文章だった。共有したいのは仕様ではなく、私が何で詰まってどう考え直したかなのに、それが全部平らに均されていた。

原因ははっきりしていた。スキル本文に構成と規範は書いたが、文体を一言も書いていなかったのだ。何も指定しなければ、AIは最も無難な書き方、つまり報告書の文体に落ちる。そこで文体の節を足し、一人称で自分の体験として書くこと、見出しは名詞ラベルではなく一文にすること、避けるべき言い回しを名指しで並べた。加えて、ゆるっと・ていねい・きっちり・実況・さくっと・ハンズオンの6種をプリセットにして、Q5 として実行時に選ばせることにした。質問は4問から5問に増えたが、これは増やす価値があった。今あなたが読んでいるこの記事は、その Q5 で「きっちり」を選んで出したものだ。

初回実行では、ほかに2つ直した。素材が多いときの分割提案をいつ出すか決めていなかったので「Q1 の選択肢として出す」と明記し、伏せ字を全か無かで扱っていたので「単体では特定できないが組み合わせると絞り込める情報は、残したうえで理由を添えて報告する」というグレーゾーン申告を仕様に昇格させた。そして最後に、その新ルールを記事自身に適用して、裏の取れていなかった数値を書き直した。使う前に想像で足したルールより、1回使って痛い目を見てから足したルールのほうが、はっきり効く。

## 真似するなら、聞く順番から先に設計するのがいい

一連の作業で一番効いたのは、質問の中身ではなく順番だった。grilling は「今聞ける質問」だけを出すという制約ひとつで、答える側の負担を劇的に下げている。答えが他の未決定に依存する質問は次のラウンドに回る。だから答える側は、仮置きなしで即答できる。

そしてその作法は、そのまま自分のスキルに輸入できた。`chat-to-article` が実行時に投げる5問も、全部に推奨案が付き、依存関係のあるものは聞かない。設計に使った道具が、成果物の中に形を変えて残った格好だ。

自作スキルは執筆時点で9個あり、うち7個はスクリプトを持たない Markdown だけのものだ。作るのが難しいという印象があるかもしれないが、実際に難しいのはファイルの書き方ではなく、何を書くべきかを見つけるほうだった。今回それを見つけたのは、私ではなく、私を問い詰めてきたAIだ。

まだ試していないことも残っている。「Gemini に貼れば同じ挙動になる」というのは設計上の主張であって、未検証だ。配布物の根幹なので、ここは実測しないと胸を張れない。

もし何かスキルを作ろうとしている方がいたら、実装を頼む前に一度だけ、AIに自分を問い詰めさせてみてほしい。私の場合は3回崩れた。あなたの場合に何回崩れたか、そしてどこで崩れたかを聞いてみたい。
