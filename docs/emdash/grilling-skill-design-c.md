<!-- title: AIに自分を問い詰めさせてからスキルを作ったら、着手前に設計が3回変わった -->

AIとのチャットを素材に記事を書き起こすスキル `chat-to-article` を作った。書いたコードは0行、成果物は Markdown 1枚だけである。作ろうと思ったのは、コミュニティに何かを共有したいのに、記事を書く手間で毎回止まっていたからだ。ただ、記事にして面白かったのは中身よりも作り方のほうだった。実装に入る前に「grilling」——AIに自分を容赦なく問い詰めさせる工程——を1回通したところ、1行も書かないうちに設計が3回崩れた。

## 「全部推奨で」の一言で、記事1本が立ち上がるものを作った

`chat-to-article` は明示呼び出し専用のスキルで、`/chat-to-article` と打つと動き出す。会話中に「これ記事にすると面白いね」と言っただけで書き始められては邪魔なので、自動発動は切ってある。

呼ばれたAIがやることは単純だ。

```
会話 → やったことの目次 → 5問の確認 → 執筆 → 秘匿情報の点検 → 保存
```

つまり、素材を集めて骨組みを立て、迷いそうな部分だけ人間に聞き、書いてから危ないものを消す。この一列が全部である。

聞かれるのはこの5つだけだ。

```
Q1 何を作った話にしますか？  → AIが推測した一行が先に出てくる
Q2 読者は誰ですか？
Q3 記事の主眼は？（成果物 / 詰まった所 / 学び）
Q4 公開範囲は？（伏せ字の強さが決まる）
Q5 文体は？（6種のプリセット）
```

要点は、全問に推奨案が付いていることだ。だから「全部推奨で」の一言で書き始まる。今読んでいるこの記事も、その一言から出てきている。Q1 だけは選択肢ではなく推測した一行を提示する形にした。初見の人が最初に「で、何の記事だっけ」と考え込むところを飛ばしたかったからだ。

実体は `SKILL.md` 1ファイル、4,000字ほど。スクリプトも外部参照もない。自分の手元にあるスキルは執筆時点で9個だが、そのうち7個は同じくスクリプトなしなので、構成としては見慣れたものである。

## grilling は「今この瞬間に聞ける質問」だけを聞いてくる

きっかけは Matt Pocock の `mattpocock/skills` だった。37個のスキルが入っている中で、作者が「最も人気があり、変更を加えるときは毎回使え」と書いているのが grilling である。本体は 2,015バイトしかない。

考え方の核はここに集約されている。

> 決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

普通のAIも「確認させてください」と質問を並べてくる。しかしその中には、上の答え次第で消滅する質問が平気で混ざっている。答える側はそこで混乱する。grilling はそれを構造的に禁じ、他の未解決の質問に依存する質問はすべて次のラウンドへ送る。

もう一つ効いたのが役割分担の明示だった。

> 事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

事実はAIが調べ、決定は人間がする。当たり前に見えるが、この線が引かれているだけで会話の質がはっきり変わる。実際、後述する 34MB は自分が知らなかった事実で、聞かれていたら答えられなかった。

これを `chat-to-article` の設計に持ち込んで、5ラウンド回した。記録に残っている設計から実装完了までの時間は1時間24分で、そのほとんどが問い詰めに費やされている。

## 崩壊1 — 作りたいのは記事ではなく、記事を作るスキルだった

ラウンド2で、AIは「どのコミュニティに出しますか」「記事1本の単位は」と聞いてきた。それらしい質問である。ただ答えていて違和感があり、途中で止めてこう言った。

> 私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

これが一番大きい崩壊だった。決めるべきことが2層に分かれていたのだ。

| 層 | 内容 | いつ決めるか |
|---|---|---|
| A スキルの仕様 | 発動方法、素材の取り方、出力先、伏せ字の仕組み | 今 |
| B 記事ごとの選択 | 読者、記事の単位、文体、公開範囲 | スキルが実行時に聞く |

読者も公開先も層Bである。スキルに焼き付けるべきは答えではなく、聞く仕組みのほうだった。気づかずに進めていたら、自分の想定した投稿先の作法が埋め込まれた、自分にしか使えないスキルができていたはずだ。正直、ここは止めるまで気持ちよく答えてしまっていた。

## 崩壊2 — 「プロジェクト全体のログを素材に」は 34MB で成立しなかった

素材の範囲は、最初「プロジェクト全体の会話ログ」と決めていた。その直後にAIが勝手に実測してきた数字がこれである。

| プロジェクト | セッション数 | 合計 |
|---|---|---|
| A | 9 | 34 MB |
| B | 1 | 15 MB |
| C | 0 | — |

34MB は文脈に入らない。さらに C のように、ログが1本も残っていないプロジェクトもある。別の場所で作業したものだ。

ここで設計は「全部読む」から「目次を作ってから必要な箇所だけ読む」に変わった。スキル本文にも、ログの全文を読もうとするなとはっきり書いてある。同じ発想でスキルを作ろうとしている方は、素材の物理サイズを先に測ることをおすすめする。想像で「ログを食わせればいい」と書くと、初回実行で詰まる。

## 崩壊3 — 配布物にした瞬間、スクリプトもファイル読み取りも使えなくなった

3つ目は、このスキルを配布物にすると決め、かつ Gemini でも動かしたいと言った時点で来た。Gemini のスキルにはプロンプト文しか登録できない。つまりスクリプトを持てず、ファイルも読めず、過去のセッションログなど存在すらしない。

崩壊2 で立てた「目次を作ってから深掘りする」という機構は、素材が読める環境の話だった。そこで、処理手順は共通にして、素材の在り処だけを環境依存にした。

```
【共通の手順】 素材から目次を作る → 必要な箇所だけ深掘りする

【素材の在り処 — 上から順に、使えるものを使う】
  1. 今の会話            ← どの環境にも必ずある
  2. 貼られた/添付されたログ
  3. 過去のセッションログ ← ファイルを読める環境のみ
```

上から使えるものを使い、1 だけでも記事は書ける、という縮退設計である。長いチャット1本で作りきったなら、その会話が全体像そのものなのだから、素材が1しかないことを謝る必要もない。スキル本文にも「謝らない・断らない」と書いた。

同じ理由で、参照ファイルに分割するのもやめて1ファイルに寄せた。分ければ Gemini では読まれず、環境ごとに挙動が変わってしまう。

## 使ってみたら、自分のスキルが要件定義書みたいな記事を出してきた

作った直後に、この会話自体を素材にして1回走らせた。仕様どおりには動いた。5問聞き、時系列をなぞらず再構成し、伏せ字も効いた。

問題は文章のほうだった。出てきたのは「〜を実現した」「〜が可能となる」の並ぶ、要件定義書のような記事だったのだ。事実は正しいのに、人が書いたブログに見えない。原因ははっきりしていて、スキル本文に構成の型は書いてあっても、文体について一行も書いていなかった。

そこで文体の節を足した。一人称で自分の体験として書くこと、見出しは名詞ラベルではなく一文にすること、結びは読者への一言で終えること。そして文体そのものを実行時に選べるよう、6種のプリセット（ゆるっと / ていねい / きっちり / 実況 / さくっと / ハンズオン）を Q5 として追加した。質問は4問から5問に増えたが、ここは増やす価値があった。読者と場が変われば、正しい文体は変わる。

実際に使ってみて直すことになったのは文体だけではない。投稿先の CMS に貼ってみたところ、Markdown をテキストのまま貼ると記号が記号のまま残り、描画済みのものを貼ると見出しも引用もコードブロックも表も、そのままブロックとして入ることが分かった。mermaid は描画されないので、図はテキストで描く方式に切り替えた。この手の話は実測するまで分からない。

## 真似するなら、順番は「問い詰め → 作る → 1回使う → 直す」

今回いちばん効いたのは、着手前にAIへ質問させたことそのものではなく、質問を依存関係の順に並べさせたことだった。思いつき順に5個並ぶ質問は答えづらいが、今答えられるものだけが来るなら答えられる。しかも推奨案が付いていれば「全部それでいい」で進む。答える側のコストが低いから、10問あっても最後まで続く。

もう一つは、作った直後に1回使ったことだ。使う前に想像で書き足した仕様より、1回使って出てきた不満のほうが正確だった。要件定義書のような記事が出てきたおかげで、文体の節という一番大きい追加ができた。

逆に、grilling は毎回使うものではないとも思っている。ボタンの色を変える依頼に設計ツリーは要らない。「一発で作らせたら、たぶん想定と違うものが出てくるな」と自分で思う依頼のときだけでいい。

## 使ってみた感想を聞かせてほしい

`chat-to-article` は、まだ自分の環境で数回動かしただけのものだ。特に、Gemini に貼れば同じ挙動になるという部分は設計上の主張であって、まだ検証できていない。配布物としては、ここが一番の弱点だと分かっている。

同じように「AIとのやり取りを記事にしたい」と思っている方がいたら、まずは grilling のほうを試してみてほしい。自作のスキルがなくても、着手前の15分として単体で効く。
