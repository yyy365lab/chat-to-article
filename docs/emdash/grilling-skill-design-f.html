この手順どおりに進めると、あなたの手元にスキルが1枚残ります

作ったのは chat-to-article という、AIとのチャットを素材に記事を書き起こすスキルです。実体は SKILL.md が1ファイル、4,000字ほど。スクリプトは1本もありません。ただ、この記事で共有したいのは中身ではなく作り方のほうです。実装に入る前に grilling(AIに自分を容赦なく問い詰めさせる工程)を1回挟んだところ、まだ1文字も書いていない段階で設計が3回ひっくり返りました。

スキルを自作するのは初めてではなかったのですが、着手前に設計が崩れるという体験は初めてで、これは道具というより手順として渡せると思ったのがこの記事を書いた理由です。あなたが作るものは何でも構いません。記録では、設計の開始から実装完了まで1時間24分でした。

前半の3つが grilling、後半の3つが実装と導入で、この6手順がそのままこの記事の目次です。

手順1 — grilling を入れて、何をする道具なのかを先に掴みます

grilling は Matt Pocock が配布しているスキル集に入っています。37個あるうちの1つで、作者自身が「最も人気のあるスキル。変更を加えるときは毎回使え」と書いているものです。中身は 2,015バイトしかありません。

導入はこの1行です。

npx skills add <owner>/<repo>

今回なら <owner>/<repo> の部分が mattpocock/skills になります。

確認ポイント。 入ったら /grill-me が候補に出るかを見てください。このスキル集は37個のうち22個が明示呼び出し専用で、会話から勝手に発動しません。「入れたのに反応しない」ではなく、そういう設計です。

先に考え方だけ押さえておくと、答える側のコストが下がります。核になるのはこの一文です。

決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

ふつうのAIも「確認させてください」と質問を並べますが、その並びには上の答え次第で消える質問が混ざっています。grilling はそれを構造的に禁じます。

実線で並んだ3つは今すぐ答えられる質問、破線でぶら下がっている「会社名は残すか」は伏せ字の方針が決まるまで聞けない質問で、grilling は後者を次のラウンドまで出してきません。

手順2 — 仕様を書かずに、一言だけ添えて呼び出します

準備はいりません。打つのはこれだけです。

/grill-me

私が添えた一言は「AIとのやり取りを記事化する、というスキルを作りたいと考えています」でした。この粒度で十分に回ります。

詰まりやすい所。 ここで「ちゃんと要件を整理してから呼ばないと失礼だ」と身構えると、grilling を使う意味が半分なくなります。役割はスキル本文にはっきり書かれています。

事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

実際、私が「プロジェクト全体のログを素材にしたい」と答えた直後、AIは手元のログを勝手に実測してきました。プロジェクトAが9セッションで34MB、Bが1セッションで15MB、Cはログが0本。34MBは文脈に入りませんし、Cのようにどこかよそで作業して記録が残っていないケースもあります。この事実は、質問として投げられていたら私には答えられませんでした。あなたが持つべきなのは調査結果ではなく決定だけです。

手順3 — ラウンドごとに答えます。迷ったら「全部推奨で」で進みます

grilling の質問には必ず推奨案が付いてきます。番号と ➡️ の行が並ぶ形式なので、そのままでよければ「全部推奨で」の一言で次のラウンドに進めます。私は5ラウンド回しました。所要時間のほとんどはここです。

ラウンド決まったこと
1素材の範囲、記事の型、出力形式、秘匿情報の扱い
2素材の取り出し機構(途中で仕切り直し)
3環境差の吸収、配布の入口、1ファイルに収めるか
4記述言語、実行時に聞く質問セット、伏せ字ルール、スキル名
5記事の構成テンプレート、引用スタイル

詰まりやすい所その1 — 目的がすり替わったら、その場で止めてください

ラウンド2で「どのコミュニティに出しますか」と聞かれました。それらしい質問なのですが、答えていて手応えがおかしい。止めてこう言いました。

私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

これで、決めることが2層に分かれていると分かりました。発動方法・素材の取り方・出力先といったスキルの仕様は今決めること。読者やトーンは記事ごとに変わることなので、スキルに埋め込むべきは答えではなく聞く仕組みのほうでした。気づかずに進んでいたら、私の投稿先が焼き付いた、私にしか使えないスキルができていたはずです。

詰まりやすい所その2 — 配布物にするなら、動く環境を先に宣言してください

私はラウンド3の手前で「これは配布物で、Gemini で使うとプロンプト1本しか登録できない」と伝えました。この一言で、スクリプトを持つ案と、私個人の作業記録を素材にする案が同時に消えました。他人の環境にない資産には依存できないからです。代わりに素材は次の縮退設計になりました。

  1. いまの会話 — どの環境にも必ずある。ここだけで成立させる
  2. ユーザーが貼った、または添付したログ — あれば加える
  3. 過去のセッションログ — ファイルを読める環境でのみ使う

確認ポイント。「フロンティアが空になりました」「これで合っているか確認させてください」と言われたら、そこが終了地点です。確認が取れるまで着手させないのが grilling の作法なので、勝手に実装が始まっていたら止めて構いません。

手順4 — SKILL.md を1ファイルだけ書きます

合意ができたら実装です。ファイルは1つ。冒頭の frontmatter に3つ書きます。

---
name: chat-to-article
description: >-
  AIとのチャットのやり取りを素材にして、記事(Markdown)を書き起こす。
  article / blog post / writeup / 記事化 / ブログ。
  USE WHEN ユーザーが「この作業を記事にしたい」と言ったとき。
  DO NOT USE WHEN 社内報告書・議事録が目的のとき。
disable-model-invocation: true
---

name は置き場所のフォルダ名と揃えます。description は発動判定に直結するので、USE WHEN と DO NOT USE WHEN を両方書いてください。日本語で書く場合も、英語のキーワードを混ぜておくと判定が安定します。

disable-model-invocation: true を付けると自動発動が切れ、/chat-to-article と自分で打ったときだけ動きます。会話の途中で「これ記事にすると面白いね」と言っただけで書き始められたら邪魔なので、私はこれを付けました。

本文は日本語の手順書にしました。スキルの言語が出力の言語を引っ張るためで、日本語の記事を書かせたいなら本文も日本語にしてください。分量は4,000字ほど、スクリプトはゼロです。手元の自作スキルは執筆時点で9個ありますが、うち7個は同じくスクリプトなしでした。1ファイルの Markdown だけで足りる範囲は、あなたが思っているより広いはずです。

手順5 — 置き場所に入れて、実際に呼びます

置き場所はここです。

~/.claude/skills/<name>/SKILL.md

置いたら呼び出します。

/chat-to-article

確認ポイント。 候補に出てこないときは、フォルダ名と frontmatter の name が一致しているかを最初に見てください。

詰まりやすい所。 リポジトリ側とこの置き場所で二重管理になります。私は最初、手でコピーして同期していました。GitHub に上げて npx skills add <owner>/<repo> で入れ直すと、この二重管理はなくなります。

手順6 — 1回使って、出てきた不満をそのまま仕様に足します

ここを飛ばさないでください。私はこの手順で一番大きい修正が出ました。

初回実行そのものは仕様どおりでした。質問の数も、時系列をなぞらない再構成も、伏せ字の報告も、保存先を勝手に決めない点も、書いたとおりに動いています。それでも出てきた記事は要件定義書のような文章でした。 事実は正確なのに、人が書いたブログには読めない。仕様に「どう書くか」が一行もなかったからです。

そこで文体の節を足し、ゆるっと・ていねい・きっちり・実況・さくっと・ハンズオンの6種をプリセットとして用意して、実行時の質問に加えました。質問は4問から5問になり、何の話か・読者・主眼・公開範囲・文体、の5つになっています。いまあなたが読んでいるこの記事は、そのうちハンズオンで書かせたものです。

同じ回で、他にも3点を仕様に昇格させました。素材が多いときの分割提案は質問を増やさず選択肢に混ぜること、伏せ字はグレーゾーンを別立てで申告すること、そして数字は素材で裏が取れるものだけ使うことです。3つ目はそのまま自分に跳ね返ってきて、初回の記事に書いていた体感まかせの所要時間を、裏の取れる言い方に書き直しました。

投稿先を実測したときにも直しが出ています。今回の投稿先は Cloudflare 製のCMSで、Markdown をテキストのまま貼ると記号がそのまま残り、ブラウザで描画した状態を貼ると見出しも引用もコードブロックも表もブロックとして入りました。mermaid は描画されなかったので、図はテキスト図解と画像に切り替えています。

真似するなら、押さえるのはこの3つです

  1. 仕様を考えてから grilling を呼ばない。 一言渡して問い詰めさせるほうが速いです
  2. 「今決めること」と「実行時に聞くこと」を分ける。 ここを混ぜたスキルは自分専用になります
  3. 1回使ってから直す。 想像で足した仕様より、使って出た不満のほうが確実に効きます

grilling は要件定義ではありません。プロジェクト単位ではなく変更単位で、着手ボタンを押す直前に毎回挟むものです。経験のある先輩に「これ作ります」と言って15分詰められる、あの15分を構造化したもの、と考えると距離感が合うと思います。

あなたが最初の1枚を作るなら、いま手作業で毎回やっている説明や整形を1つ選ぶのがおすすめです。私の1つ前の自作スキルも「GitHubリポジトリを初心者向けに解説する」で、会話で実際にやっていたことを手順に落としただけでした。作ってから足りない部分を SKILL.md に足していく、その順番が一番早い育て方です。

同じ手順でやってみて、grilling が思わぬ所で刺さった、あるいは全然かみ合わなかったという話があれば、ぜひ聞かせてください。私の次の宿題は、この1ファイル設計が Claude Code 以外でも本当に同じ挙動になるかを実測することです。
