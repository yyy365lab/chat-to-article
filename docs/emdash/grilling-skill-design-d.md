## 「記事化スキルを作りたい」と言った瞬間から、AI が質問を返してきました

作ったのは `chat-to-article` という記事化スキルです。AI とのチャットを素材にして、コミュニティ共有用の記事を書き起こす。実体は `SKILL.md` が1枚、4,000字ほど。スクリプトも外部ファイルもありません。

ただ今日書きたいのは中身より作り方のほうで、実装に入る前に **grilling**(問い詰め)という工程を挟みました。AI に自分を容赦なく質問攻めにさせるやつです。結果、1行も書かないうちに設計が3回ひっくり返りました。

以下、山場だけ実際のやり取りで並べます。時系列を全部は追いません 🙂

## まず、grilling が「今聞ける質問」しか出さない

きっかけは Matt Pocock さんの [mattpocock/skills](https://github.com/mattpocock/skills) でした。スキルが37個入っていて、作者が「いちばん人気。変更を加えるときは毎回使え」と書いているのが `grill-me`。本体を読ませたら 2,015バイトしかありませんでした。

核はここです。

> 決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

図にするとこうなります。

```
    「記事化スキルを作る」
     ├─ 素材はどこから？   ← 今聞ける
     ├─ 出力はどこへ？     ← 今聞ける
     └─ 引用はどう見せる？ ← 今聞ける
          └─ 引用の書式は？      ← 「引用する」と決まるまで聞けない
               └─ 何行まで？      ← さらにその後
```

つまり、上の答え次第で消える質問を今ぶつけるな、というルールです。ふつうの AI が5個くらい質問を並べてきて答えづらいのは、この混線が原因だったんですね。

そして役割分担がはっきり書いてあります。

> 事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

これを、ちょうど作りたかった記事化スキルの設計にそのまま突っ込みました。ラウンド1が始まります。

## ラウンド2で「作りたいのは記事じゃない」と止めました

AI は素材の絞り込み方を聞いてきたあと、「どのコミュニティに出しますか？」「記事1本の単位は？」と聞いてきました。それらしい質問です。でも答えていて、どんどん気持ち悪くなってきた。

こちらから止めました。

> 私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

AI の返しが早かった。決めることが2層に分かれていた、と言うんです。**層A がスキルの仕様**(発動方法・素材の取り方・出力先・伏せ字の仕組み)で、いま決めるもの。**層B は記事ごとに変わる選択**(読者・主眼・公開範囲・文体)で、スキルが実行時に聞くもの。

さっきの質問は全部、層B でした。スキルに焼き付けるべきは答えではなく「聞く仕組み」だったわけです 💡

ここに気づかず進んでいたら、自分の投稿先の設定が固まった、自分にしか使えないスキルができていました。崩壊1です。

## 「34MB」という数字が出てきて、素材の設計が消えました

素材はプロジェクト全体の会話ログにしたい、と伝えたところで、AI が勝手に実測してきました。ログの実体は `~/.claude/projects/` 配下の jsonl です。

結果は、プロジェクト A が 9セッションで 34MB、B が 1セッションで 15MB、そして C はログが 0本。C は別の場所で作業していたので、そもそも残っていませんでした。

34MB は文脈に入りません。「プロジェクト全体を素材に」という発想は、物理的に成立しなかった。

ここは grilling の「事実は AI が調べる」が効いた場面でした。こちらは何MBになるかなんて知らないので、**聞かれていたら答えられませんでした**。崩壊2。

## 「配布物です」と言った途端、設計が大きく崩れました

とどめは自分の一言でした。このスキルは配布したい、そして Gemini でも同じ挙動にしたい、と。返ってきたのがこれです。

> 重要な制約が2つ確定しました。配布物であることと、Gemini ではプロンプト1本しか登録できないこと。これで設計が大きく変わります。

帰結は聞くまでもありませんでした。配布物なら、自分の手元にしかない記録データには依存できません。プロンプト1本ならスクリプトを持てず、ファイルも読めません。そして Gemini には `~/.claude/projects/` 自体が存在しません。

さっきまで議論していた「34MB 問題」は、Claude Code のときだけ起きるローカルな問題だったわけです。Gemini では逆に「素材が目の前の会話しかない」という別の問題になる。崩壊3 🔥

そこで、処理手順は共通にして、**素材の在り処だけを環境依存にする**設計に落ち着きました。

`今の会話 💬 → 貼られたログ 📄 → 読めるなら過去セッション 🗂️`

上から順に、使えるものを使う。**1 だけでも記事は書ける**のが肝です。Gemini で長いチャット1本で作りきったなら、その会話こそがプロジェクト全体ですから。

## できたものと、5ラウンド回した実感

そんなわけで、5ラウンドの問い詰めを経て仕様が固まりました。記録では、設計から実装完了まで1時間24分。そのほとんどが grilling で、実装は終盤のごく一部です。

使い方は `/chat-to-article` と打つだけ。AI が会話から「何をやったか」の目次を内部で作って、質問を5つだけ返してきます。何の話にする / 読者は誰 / 主眼はどこ / 公開範囲は / 文体は。全部に推奨案が付くので「全部推奨で」の一言で書き始まります。この記事もその一言から出ています。

伏せ字も既定で入ります。個人名・社名・パスを置き換えたうえで、記事には「※社名は伏せました」と**書かない**。伏せた事実自体が情報になるので、何を置換したかはチャットのほうで報告する仕組みです。

自作スキルは執筆時点で9個あって、うち7個はスクリプトなし。今回もその形に揃えました。1枚なので、Gemini に貼れば同じものが動きます。

## 使ってみたら、AI が自分の記事にダメ出しを始めました

作ったら試したくなるので、この会話自体を素材に1回回してみました。仕様どおりには動いたんですが、そのあと AI がこう言い出したんです。

> 「10分」は裏が取れていませんでした

記事の中に「実装そのものは10分だった」と書いていて、それが体感だった、という自己申告です。記録に残っているのはラン全体の1時間24分だけ。というわけで「そのほとんどは grilling で、実装は終盤のごく一部」と、裏の取れる事実だけで言い直しました。

この件を含めて3点をスキル本体に昇格させています。分割提案は Q1 の選択肢として出すこと、伏せ字のグレーゾーンは残したうえで理由を添えて報告すること、そして**数字は素材で裏が取れるものだけ使うこと**。想像で書いたルールより、1回使って出た穴を塞ぐほうが確実に効きました。

そのあともう1つ直しています。初回に出てきた記事が、正しいのに要件定義書みたいだったんですよ 😇 なので文体の節を足して、ゆるっと / ていねい / きっちり / 実況 / さくっと / ハンズオン の6種を Q5 として追加しました。質問は4問から5問に増えています。この記事は「実況」で書いたやつです。

投稿先の CMS もクセがあって、Markdown をテキストのまま貼ると記号が記号のまま残りました。描画済みのほうを貼ったら見出しも引用もコードブロックもブロックとして入ります。mermaid は描画されなかったので、図はテキストで描く方式に決めました。

## 同じところで詰まりそうな方へ

一番の学びは、**AI に「決めていないこと」を先に全部言わせると、着手前に壊れる**ということでした。壊れるのは早いほうが安いです。実装後に3つ見つかっていたら、たぶん作り直していました。

そして grilling が効いたのは、AI が賢かったからというより「聞ける質問しか聞かない」「事実は自分で調べる」「決定は人間に返す」の3つが構造として書いてあったからだと思っています。2KB でこれが書けるんだな、というのが正直な驚きでした。

作りかけの何かを持っている方は、着手ボタンを押す直前に一度 grilling をかけてみてください。10分で「思ってたより決めることが多かった」となるはずです 👋 うまくいかなかった例も聞いてみたいです。
