「記事化スキルを作りたい」と言ったら、AI が質問を返してきました

作ったのは chat-to-article という記事化スキルです。AI とのチャットを素材にして、コミュニティ共有用の記事を書き起こすもの。実体は SKILL.md が1枚、4,000字ほどで、スクリプトも外部ファイルもありません。

ただ、今日ここに書きたいのは中身より作り方のほうです。実装に入る前に grilling(問い詰め)という工程を挟みました。AI に自分を容赦なく質問攻めにさせるやつです。結果、1行も書かないうちに設計が3回ひっくり返りました。

以下、そのときのやり取りを山場だけ並べます。順番を全部は追いません 🙂

最初に読ませた 2,015バイトが、質問の出し方を縛っていました

きっかけは Matt Pocock さんの mattpocock/skills でした。スキルが37個入っていて、作者が「いちばん人気。変更を加えるときは毎回使え」と書いているのが grill-me。中身を読ませたら、本体は 2,015バイトしかありませんでした。

核はこの一文です。

決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

読んだだけだとピンと来なかったので、自分の案件に当てはめて図にしてみました。

つまり、上の答え次第で消えてしまう質問は、いま聞いてはいけない、ということです。

ふつうの AI も「確認させてください」と質問を並べてきます。あれが答えづらいのは、この混線が入っているからだったんですね 💡 grilling はそれを構造として禁じていました。

役割分担もはっきり書いてありました。

事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

これを、ちょうど作りたかった記事化スキルの設計にそのまま突っ込みました。ラウンド1が始まります。

ラウンド2で「作りたいのは記事じゃない」と止めました

AI は素材の絞り込み方を聞いたあと、「どのコミュニティに出しますか？」「記事1本の単位は？」と続けてきました。それらしい質問です。でも答えているうちに、だんだん気持ち悪くなってきました 🤔

こちらから止めました。

私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

返しが早かったです。決めることが2層に分かれていた、と言ってきました。層A がスキルの仕様(発動方法・素材の取り方・出力先・伏せ字の仕組み)で、いま決めるもの。層B は記事ごとに変わる選択(読者・主眼・公開範囲)で、スキルが実行時に聞くもの。

さっきの質問は全部、層B でした。スキルに焼き付けるべきは答えではなく「聞く仕組み」だったわけです。

気づかず進んでいたら、自分の投稿先の設定が固まった、自分にしか使えないスキルになっていました。これが崩壊1です。

「34MB」という数字が出てきて、素材の設計が消えました

素材はプロジェクト全体の会話ログにしたい、と伝えたところで、AI が勝手に実測してきました。Claude Code のログは ~/.claude/projects/ の下に jsonl で残っています。

結果は、プロジェクト A が 9セッションで 34MB、B が 1セッションで 15MB、そして C はログが 0本。C は別の場所で作業していたので、そもそも残っていませんでした。

34MB は文脈に入りません。「プロジェクト全体を素材に」という発想は、物理的に成立していなかった。

ここは、さっきの「事実は AI が調べる」がそのまま効いた場面でした。こちらは何MBになるかなんて知らないので、聞かれていたら答えられませんでした。崩壊2です。

「配布物です」と言った途端、いちばん大きく崩れました 🔥

とどめは自分の一言でした。このスキルは配布したい、そして Gemini でも同じ挙動にしたい、と。返ってきたのがこれです。

重要な制約が2つ確定しました。配布物であることと、Gemini ではプロンプト1本しか登録できないこと。これで設計が大きく変わります。

そこから先は、聞かれるまでもない帰結でした。配布物なら、自分の手元にしかない記録データには依存できません。プロンプト1本ならスクリプトを持てず、ファイルも読めません。そして Gemini には ~/.claude/projects/ 自体が存在しません。

さっきまで悩んでいた「34MB 問題」は、Claude Code のときだけ起きるローカルな問題だった、ということです。Gemini では逆に「素材が目の前の会話しかない」という別の問題になる。崩壊3。

そこで、処理の手順は共通にして、素材の在り処だけを環境依存にする設計に落ち着きました。

上から順に、使えるものを使う。いちばん左だけでも記事は書けるのが肝です。

Gemini で長いチャット1本で作りきったなら、その会話こそがプロジェクト全体ですから。読めるログがある環境では素材が厚くなる、という積み増しの形にしました。

5ラウンドで仕様が固まって、できたのは1枚でした

そんなわけで、問い詰めは5ラウンドで終わりました。記録では、設計から実装完了まで1時間24分。そのほとんどが grilling で、実装は終盤のごく一部です。

使い方は /chat-to-article と打つだけ。AI が会話から「何をやったか」の目次を内部で作って、質問を5つだけ返してきます。

Q1 何を作った話にしますか？  ➡️ <AI が推測した一行>
Q2 読者は誰ですか？          ➡️ (b) 特定の技術コミュニティ
Q3 記事の主眼は？            ➡️ (a) 成果物の紹介
Q4 公開範囲は？              ➡️ (a) 一般公開
Q5 文体は？                  ➡️ (d) 実況

全部に推奨案が付くので、「全部推奨で」の一言で書き始まります。いま読んでいるこの記事も、その一言から出ています。

伏せ字も既定で入ります。個人名・社名・パスを置き換えたうえで、記事には「※社名は伏せました」と書かない。伏せた事実自体が情報になるので、何を置換したかはチャットのほうで報告する仕組みにしました。

自作スキルは執筆時点で9個あって、うち7個はスクリプトなし。今回もその形に揃えています。1枚なので、Gemini に貼れば同じものが動くはずです。

使ってみたら、AI が自分の書いた記事にダメ出しを始めました 😇

作ったら試したくなるので、この会話自体を素材に1回回してみました。仕様どおりには動いたんですが、そのあと AI がこう言い出したんです。

「10分」は裏が取れていませんでした(記録に残っているのはラン全体の1時間24分だけです)。

記事の中に「実装そのものは10分だった」と書いていて、それが体感だった、という自己申告でした。というわけで「そのほとんどは grilling で、実装は終盤のごく一部」と、裏の取れる事実だけで言い直しています。

この件を含めて3点をスキル本体に昇格させました。分割の提案は Q1 の選択肢として出すこと、伏せ字のグレーゾーンは残したうえで理由を添えて報告すること、そして数字は素材で裏が取れるものだけ使うこと。想像で書いたルールより、1回使って出た穴を塞ぐほうが確実に効きました。

そのあともう1つ直しています。初回に出てきた記事が、正しいのに要件定義書みたいだったんですよ。なので文体の節を足して、ゆるっと / ていねい / きっちり / 実況 / さくっと / ハンズオン の6種を Q5 として追加しました。質問は4問から5問に増えています。この記事は「実況」で書いたやつです。

投稿先の CMS にもクセがありました。Markdown をテキストのまま貼ると記号が記号のまま残るのに、描画済みのほうを貼ると見出しも引用もコードブロックも表もブロックとして入る。mermaid は描画されなかったので、図は画像とテキストで描く方式に決めました。

着手ボタンの直前に、一度かけてみてください 👋

いちばんの学びは、AI に「決めていないこと」を先に全部言わせると、着手前に壊れるということでした。壊れるのは早いほうが安いです。実装後に3つ見つかっていたら、たぶん作り直していました。

そして grilling が効いたのは、AI が賢かったからというより、「聞ける質問しか聞かない」「事実は自分で調べる」「決定は人間に返す」の3つが構造として書いてあったからだと思っています。2KB でこれが書けるんだな、というのが正直な驚きでした。

作りかけの何かを持っている方は、着手ボタンを押す直前に一度 grilling をかけてみてください。10分で「思ってたより決めることが多かった」となるはずです。うまくいかなかった例も聞いてみたいです。
