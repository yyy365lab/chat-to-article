AIとのチャットを素材に記事を書き起こすスキル chat-to-article を作った。書いたコードは0行で、成果物は Markdown 1枚しかない。作ろうと思ったのは、共有したい話はあるのに、記事を書く手間のところで毎回止まっていたからだ。ただ、あとから振り返って面白かったのは中身よりも作り方のほうだった。実装に入る前に「grilling」——AIに自分を容赦なく問い詰めさせる工程——を1回通したら、1行も書かないうちに設計が3回崩れた。

「全部推奨で」の一言で記事が立ち上がるものができた

chat-to-article は明示呼び出し専用のスキルで、/chat-to-article と打つと動き出す。会話の途中で「これ記事にすると面白そう」と言っただけで書き始められては困るので、自動発動は切ってある。

呼ばれたAIの動きは一列だ。

素材から骨組みを立て、迷いそうな部分だけ人間に聞き、書いてから危ないものを消す。やることはこれだけである。

途中で聞かれるのは5つだけだ。

Q1 何を作った話にしますか？  → AIが推測した一行が先に出てくる
Q2 読者は誰ですか？
Q3 記事の主眼は？（成果物 / 詰まった所 / 学び）
Q4 公開範囲は？（伏せ字の強さがここで決まる）
Q5 文体は？（プリセット6種から）

肝は全問に推奨案が付いていることで、だから「全部推奨で」の一言で書き始まる。いま読んでいるこの記事も、その一言から出てきたものだ。Q1 だけは選択肢ではなく、推測した一行を提示する形にした。初見の人が最初に「で、何の記事だっけ」と考え込む数分を消したかった。

実体は SKILL.md 1ファイル、4,000字ほど。スクリプトも外部参照もない。手元にあるスキルは執筆時点で9個だが、うち7個は同じくスクリプトなしなので、構成としては見慣れたものになった。

grilling は「今この瞬間に答えられる質問」だけを投げてくる

きっかけは Matt Pocock の mattpocock/skills だった。37個のスキルが入っている中で、作者が「最も人気があり、変更を加えるときは毎回使え」と書いているのが grilling である。本体は 2,015バイトしかない。

考え方の核はこの一文に集約されている。

決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

上段の3つが今答えられる質問で、その下にぶら下がる質問（枠が白いもの）は上の答えが出るまで存在すらしない、というのがこの図だ。

普通のAIも「確認させてください」と質問を並べてくる。しかしその中には、上の答え次第で消滅する質問が平気で混ざっている。答える側が混乱するのはそこだ。grilling はそれを構造的に禁じ、他の未解決の質問に依存する質問はすべて次のラウンドへ送る。

もう一つ効いたのが、役割分担がはっきり書いてあることだった。

事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

事実はAIが調べ、決定は人間がする。当たり前に見えて、この線が引かれているだけで会話の質が変わる。実際、後で出てくる 34MB は自分がまったく知らなかった数字で、質問されていたら答えられなかった。

これを chat-to-article の設計にそのまま持ち込み、5ラウンド回した。記録に残っている設計から実装完了までの時間は1時間24分で、そのほとんどが問い詰めに費やされている。

崩壊1 — 作りたかったのは記事ではなく、記事を作る仕組みだった

ラウンド2で、AIは「どのコミュニティに出しますか」「記事1本の単位は」と聞いてきた。もっともらしい質問である。ただ答えながら違和感が募り、途中で止めてこう言った。

私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

これが一番大きい崩壊だった。決めるべきことが、実は2層に分かれていたのだ。

層内容いつ決めるか
A スキルの仕様発動方法、素材の取り方、出力先、伏せ字の仕組み今
B 記事ごとの選択読者、記事の単位、文体、公開範囲スキルが実行時に聞く

読者も公開先も層Bである。スキルに焼き付けるべきは答えではなく、聞く仕組みのほうだった。気づかず進めていたら、自分の想定した投稿先の作法が固定された、自分にしか使えないスキルができていたはずだ。正直に言えば、止めるまでは気持ちよく答えてしまっていた。

崩壊2 — 「プロジェクト全部のログ」は 34MB で成立しなかった

素材の範囲は、はじめ「プロジェクト全体の会話ログ」と決めていた。その直後、AIが誰にも聞かずに実測してきた数字がこれである。

プロジェクトセッション数合計
A934 MB
B115 MB
C0—

34MB は文脈に入る量ではない。しかも C のように、ログが1本も残っていないプロジェクトもある。別の場所で作業したものだ。

ここで設計は「全部読む」から「目次を作ってから必要な箇所だけ読む」に変わった。スキル本文にも、ログの全文を読もうとするな、とはっきり書いてある。同じ発想でスキルを作ろうとしている方には、素材の物理サイズを先に測ることをすすめたい。「ログを食わせればいい」と想像で書くと、初回実行の一発目で詰まる。

崩壊3 — 配布物にすると決めた瞬間、スクリプトが消えた

3つ目は、これを配布物にすると決め、なおかつ Gemini でも同じように動かしたいと言った時点で来た。Gemini のスキルにはプロンプト文しか登録できない。スクリプトは持てず、ファイルも読めず、過去のセッションログなど存在すらしない。

崩壊2 で立てた「目次を作ってから深掘りする」という機構は、素材が読める環境の話だった。そこで処理手順のほうは共通に固定し、素材の在り処だけを環境依存にした。

【共通の手順】 素材から目次を作る → 必要な箇所だけ深掘りする

【素材の在り処 — 上から順に、使えるものを使う】
  1. 今の会話             ← どの環境にも必ずある
  2. 貼られた/添付されたログ
  3. 過去のセッションログ  ← ファイルを読める環境のみ

上から使えるものを使い、1 だけでも記事は書ける。長いチャット1本で作りきったなら、その会話こそが全体像なのだから、素材が1つしかないことを謝る必要もない。スキル本文には「謝らない・断らない」と書いた。

同じ理由で、参照ファイルへの分割もやめて1ファイルに寄せた。分ければ Gemini では読まれず、環境ごとに挙動が変わる。配布物としては、それが一番まずい。

使ってみたら、自分のスキルが要件定義書みたいな記事を書いてきた

作った直後に、この会話自体を素材にして1回走らせた。仕様どおりには動いた。質問は5つ、時系列をなぞらず再構成し、伏せ字も効いている。

問題は文章のほうだった。出てきたのは「〜を実現した」「〜が可能となる」が並ぶ、要件定義書のような記事だったのだ。事実は正しいのに、人が書いたブログには見えない。原因ははっきりしていて、スキル本文に構成の型は書いてあっても、文体について一行も書いていなかった。

そこで文体の節を足した。一人称で自分の体験として書くこと、見出しは名詞ラベルではなく一文にすること、結びは読者への一言で終えること。あわせて文体自体を実行時に選べるよう、6種のプリセット（ゆるっと / ていねい / きっちり / 実況 / さくっと / ハンズオン）を Q5 として追加した。質問は4つから5つに増えたが、ここは増やす価値があった。読者と場が変われば、正しい文体も変わる。

直したのは文体だけではない。投稿先の CMS に貼って試したところ、Markdown をテキストのまま貼れば記号は記号のまま残り、描画済みのものを貼れば見出しも引用もコードブロックも表もブロックとして入ることが分かった。mermaid は描画されなかったので、図はテキストか画像で持つ方式に切り替えた。この手のことは、実際に貼ってみるまで分からない。

真似するなら「問い詰める → 作る → 1回使う → 直す」の順がいい

今回いちばん効いたのは、着手前にAIへ質問させたことそのものではなく、質問を依存関係の順に並べさせたことだった。思いつき順に5個並ぶ質問は答えづらいが、今答えられるものだけが来るなら答えられる。しかも推奨案が付いていれば「全部それでいい」で進む。答える側のコストが低いから、質問が10個あっても最後まで持つ。

もう一つは、作った直後に1回使ったことだ。使う前に想像で書き足した仕様より、1回使って出てきた不満のほうが正確だった。要件定義書のような記事が出てきたおかげで、文体の節という一番大きい追加ができている。

逆に、grilling は何にでも使うものではないとも思う。ボタンの色を変える依頼に設計ツリーは要らない。「一発で作らせたら、たぶん想定と違うものが出てくるな」と自分で思う依頼のときだけでいい。

Gemini での検証がまだ残っている

chat-to-article は、まだ自分の環境で数回動かしただけのものだ。とくに「Gemini に貼れば同じ挙動になる」という部分は設計上の主張であって、検証できていない。配布物としては、そこが最大の弱点だと分かっている。

同じように「AIとのやり取りを記事にしたい」と思っている方がいたら、まず grilling のほうを試してみてほしい。自作のスキルがなくても、着手前の15分として単体で効く。
