## 一行も書かないうちに、設計が3回ひっくり返りました

AIとのチャットのやり取りを素材にして記事を書き起こすスキル `chat-to-article` を作りました。中身は Markdown が1枚だけで、コードは書いていません。

ただ、今回お伝えしたいのは成果物そのものよりも作り方のほうです。実装に入る前に「grilling(問い詰め)」という工程を挟みました。AIに私を容赦なく質問攻めにさせる、それだけの手順です。その結果、まだ1行も書いていない段階で設計が3回崩れました。普通に「記事化スキルを作って」と頼んでいたら、この3つは全部作ったあとに判明していたはずです。

自分でスキルを作ってみたいけれど、何から決めればいいか分からない。そういう方に、いちばん効いたのが「決める順番」だった話をします。

## できあがったのは、5つ質問して記事を書く1枚のファイルです

`chat-to-article` は、`/chat-to-article` と打つと動きます。AIはまず会話を読んで「何をやったか」の目次を内部で作り、そのうえで5つだけ質問してきます。

何の話にするか、読者は誰か、記事の主眼はどこか、公開範囲はどこまでか、そして文体をどうするか。この5つです。全部に推奨案が付いてくるので、「全部推奨で」の一言でも書き始まります。実際、この記事もその一言から生まれました。

処理の流れそのものは、こうなっています。

```
会話 → 目次 → 5つの質問 → 執筆 → 伏せ字の点検 → 出力
```

つまり、素材から目次を作るところと、公開前に秘匿情報を潰すところが、必ず両端に入るという形です。

実体は `SKILL.md` が1ファイル、4,000字ほど。スクリプトも外部ファイルもありません。私が今までに作った自作スキルは9個ありますが、そのうち7個は同じくスクリプトなしで動いています。Markdown 1枚で成立するというのは、思っていたより広い範囲で通用します。

## 問い詰めの正体は、「いま聞ける質問だけを聞く」ことでした

きっかけは Matt Pocock さんが公開している mattpocock/skills でした。37個のスキルが入っていて、作者が「最も人気があり、変更を加えるときは毎回使え」と書いているのが grilling です。実物を開いてみたら 2,015バイトしかありませんでした。原稿用紙2枚ちょっとです。

核になっている考え方は、この一文に凝縮されています。

> 決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

普通のAIも「確認させてください」と質問を並べてきます。ただ、その中には上の答え次第で消えてなくなる質問が混ざっていて、答える側が混乱します。grilling はそれを構造的に禁じています。図にするとこういう形です。

```
    「予約機能をつくる」
     ├─ 誰が予約できる？   ← いま聞ける
     ├─ 重複を許す？       ← いま聞ける
     └─ 承認フローは？     ← いま聞ける
          └─ 承認者は誰？   ← 「承認あり」が
                              決まるまで聞けない
```

上の段が埋まるまで、下の段は質問として存在してはいけない。それだけのルールです。

もうひとつ効いたのが、役割分担をはっきり書いている部分でした。

> 事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

事実はAIが調べる、決定は人間がする。この線引きが、次に書く2回目の崩壊で効いてきます。

## 1回目の崩壊は、「作りたいのは記事ではなくスキルだ」でした

ラウンド2で、AIは「どのコミュニティに出しますか」「記事1本の単位はどうしますか」と聞いてきました。それらしい質問なのですが、答えながらどうにも噛み合わない感じがして、途中で止めてこう言いました。

> 私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

これが一番大きい崩壊でした。決めるべきことが、実は2つの層に分かれていたのです。

| 層 | 内容 | いつ決めるか |
|---|---|---|
| A スキルの仕様 | 発動方法、素材の取り方、出力先、伏せ字の仕組み | いま |
| B 記事ごとの選択 | 読者、記事の単位、文体、公開範囲 | スキルが実行時に聞く |

読者も公開先も層Bです。スキルに焼き付けるべきなのは答えではなく「聞く仕組み」のほうでした。気づかないまま進んでいたら、特定の投稿先の作法が埋め込まれた、自分にしか使えないスキルができていたと思います。

同じ罠は、たぶんスキル作り全般にあります。もし何かをスキル化しようとしているなら、決めようとしている項目が「毎回変わるもの」かどうかを一度疑ってみてください。

## 2回目の崩壊は、実測された34MBでした

「プロジェクト全体の会話ログを素材にする」と決めた直後、AIが勝手に手元のログを数えてきました。あるプロジェクトは9セッションで合計34MB、別のプロジェクトは1セッションで15MB、そして3つ目はログが0本でした。

34MBは文脈に入りません。しかも、ログがまったく残っていないプロジェクトもある。別の場所で作業したものです。

ここは「事実はAIが調べる」がそのまま効いた場面でした。私は「プロジェクト全体を素材に」と発想しただけで、それが物理的に何MBになるかは知らなかったからです。聞かれていたら答えられませんでした。正直、少し驚きました。設計の穴が、私の頭ではなくファイルシステムの側から出てきたわけです。

## 3回目の崩壊で、スクリプト前提の設計が消えました

3つ目は、私自身が出した制約でした。このスキルは配布するつもりで、Gemini でも同じように動いてほしい。ところが Gemini ではプロンプト1本しか登録できません。

ここでいくつかの前提が同時に潰れました。個人のダッシュボード資産に頼る設計は、他人の環境にそれが存在しないので使えない。ログを抽出するスクリプトも、置き場所がないので使えない。過去のセッションログを読む前提も、環境によっては読むファイルそのものが存在しない。

そこで、素材の在り処だけを環境依存にして、処理の手順は共通にしました。

1. いまの会話。どの環境にも必ずあります
2. ユーザーが貼った、または添付したログ
3. 過去のセッションログ。ファイルを読める環境のときだけ

上から順に、使えるものを使う。肝は1だけでも記事が書けることです。長いチャット1本で作りきったプロジェクトなら、その会話が全体像そのものなので、素材が足りないと謝る必要はありません。スキル本文にも「謝らない・断らない」と書き込みました。

## 使ってみたら、いちばん足りなかったのは文体でした

grilling を5ラウンド回して仕様を固め、そのまま実装しました。設計から実装完了までの記録は1時間24分です。そのほとんどが問い詰めで、実装は終盤のごく一部でした。

そして、できたスキルで最初の1本を書かせてみたところ、仕様どおりには動いたものの、出てきた記事が要件定義書のような文章でした。名詞の見出しが並び、体言止めの箇条書きが続く。事実は正しいのに、人が書いたブログには見えないのです。

そこで文体の節を足し、質問を4つから5つに増やしました。5つ目が「文体は?」で、ゆるっと・ていねい・きっちり・実況・さくっと・ハンズオンの6種類から選びます。文末をどうするか、絵文字を使うか、箇条書きをどこまで許すかが、プリセットごとに変わる形です。この記事は「ていねい」で書いています。

投稿先の作法も、実際に貼ってみて分かったことがありました。この記事を出している EmDash では、Markdown をテキストのまま貼ると記号がそのまま残ってしまい、描画済みの状態を貼ると見出しも引用もコードブロックも表も、そのままブロックとして入りました。mermaid は描画されなかったので、図は全部テキストで描くことにしました。ついでに、EmDash 自体を立ち上げるときに有料プラン専用の設定を外し、セッション周りの重複エラーを直しています。

## 真似するなら、質問の順番から入るのがおすすめです

今回いちばん持ち帰りになったのは、grilling そのものよりも「質問には順番がある」という一点でした。答えが他の未解決の質問に依存する質問は、いま聞いても意味がない。この規律だけで、対話の質がはっきり変わります。

あわせて、推奨案を必ず付けるという作法も効きました。答える側は「全部それでいい」と返せば済むので、質問が10個あっても止まりません。答えるコストが低いから最後まで走る、という設計です。私は自分のスキルの質問文にもこれをそのまま持ち込みました。

もうひとつ。使う前に想像で仕上げようとしないほうがよさそうです。文体の問題も、投稿先で記号が残る問題も、1回動かすまで気づけませんでした。作ったら早めに1本流してみて、出てきたものを見てから直す。そのほうが確実です。

同じように自作スキルを育てている方がいたら、最初の1回で何が壊れたかをぜひ聞かせてください。私はこれから Gemini で同じ挙動になるかを確かめるつもりです。配布物としては、そこが確かめられていないと意味がないので。
