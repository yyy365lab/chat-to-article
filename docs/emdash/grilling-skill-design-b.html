コードを書き始める前に、設計が3回ひっくり返りました

AIとのチャットのやり取りを素材にして記事を書き起こすスキル、chat-to-article を作りました。実体は Markdown が1枚だけで、コードは1行も書いていません。

ただ、今回お伝えしたいのは成果物よりも作り方のほうです。実装に入る前に grilling(問い詰め) という工程を挟みました。AIに私を容赦なく質問攻めにさせる、それだけの手順です。結果として、まだ何も書いていない段階で設計が3回崩れました。普通に「記事化スキルを作って」と頼んでいたら、この3つはおそらく全部、作り終えたあとに判明していたはずです。

スキルという仕組みは知っているけれど自分で作ったことはない、という方に向けて書いています。私にいちばん効いたのは、スキルの書き方ではなく決める順番のほうでした。

できたのは、5つ質問してから記事を書く1枚のファイルです

/chat-to-article と打つと、AIはまず会話を読んで「何をやったか」の目次を内部で作ります。そのうえで、5つだけ質問してきます。何の話にするか、読者は誰か、記事の主眼はどこか、公開範囲はどこまでか、そして文体をどうするか。この5つです。

全部に推奨案が付いてくるので、答えるのが面倒なら「全部推奨で」の一言で書き始まります。実際、いま読んでいただいているこの記事も、その一言から生まれました。

つまり、素材から目次を作る工程と、公開前に秘匿情報を潰す工程が、必ず両端に入るという形です。

実体は SKILL.md が1ファイル、4,000字ほど。スクリプトも外部ファイルもありません。私がこれまでに作った自作スキルは9個ありますが、そのうち7個は同じくスクリプトなしで動いています。Markdown 1枚で成立する範囲は、思っていたよりずっと広いというのが実感です。

問い詰めの正体は「いま聞ける質問だけを聞く」でした

きっかけは Matt Pocock さんが公開している mattpocock/skills でした。37個のスキルが入っていて、作者が「最も人気があり、変更を加えるときは毎回使え」と書いているのが grilling です。実物を開いてみたら 2,015バイトしかありませんでした。原稿用紙2枚ちょっとです。

核になっている考え方は、この一文に凝縮されていました。

決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

普通のAIも「確認させてください」と質問を並べてきます。ただ、その中には上の答え次第で消えてなくなる質問が混ざっていて、答える側が混乱します。grilling はそれを構造として禁じています。

上の段が埋まるまで、下の段は質問として存在してはいけない。ルールとしてはそれだけです。

もうひとつ、私が唸ったのは役割分担をはっきり書いている部分でした。

事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

事実はAIが調べる、決定は人間がする。この線引きが、2回目の崩壊でそのまま効いてきます。

1回目 — 私が作りたかったのは、記事ではなくスキルでした

ラウンド2で、AIは「どのコミュニティに出しますか」「記事1本の単位はどうしますか」と聞いてきました。それらしい質問なのですが、答えながらどうにも噛み合わない感じがあって、途中で止めてこう言いました。

私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

これが一番大きい崩壊でした。決めるべきことが、実は2つの層に分かれていたのです。読者も公開先も、スキルの仕様ではなく記事ごとに変わる選択のほうでした。

層中身いつ決めるか
A スキルの仕様発動方法、素材の取り方、出力先、伏せ字の仕組みいま
B 記事ごとの選択読者、記事の単位、文体、公開範囲スキルが実行時に聞く

スキルに焼き付けるべきなのは答えではなく「聞く仕組み」でした。気づかないまま進んでいたら、特定の投稿先の作法が埋め込まれた、自分にしか使えないスキルができあがっていたと思います。

同じ罠は、たぶんスキル作り全般にあります。何かをスキル化しようとしている方は、いま決めようとしている項目が「毎回変わるもの」ではないか、一度疑ってみてください。

2回目 — 34MBという数字は、私の頭からは出てきませんでした

「プロジェクト全体の会話ログを素材にする」と決めた直後、AIが勝手に手元のログを数えてきました。あるプロジェクトは9セッションで合計34MB、別のプロジェクトは1セッションで15MB、そして3つ目はログが0本。

34MBは文脈に入りません。しかも、ログがまったく残っていないプロジェクトもある。別の場所で作業したものです。素材を全部読ませる前提は、この時点で消えました。代わりに「目次を先に作り、記事に使う箇所だけ深掘りする」という二段構えになっています。

ここは「事実はAIが調べる」がそのまま効いた場面でした。私は「プロジェクト全体を素材に」と発想しただけで、それが物理的に何MBになるかは知りません。聞かれていたら答えられませんでした。設計の穴が、自分の頭ではなくファイルシステムの側から出てきたのは、正直なところ少し驚きました。

3回目 — 配布すると決めた瞬間、スクリプト前提が消えました

3つ目は、私自身が出した制約でした。このスキルは配布するつもりで、Gemini でも同じように動いてほしい。ところが Gemini ではプロンプト1本しか登録できません。

ここでいくつもの前提が同時に潰れました。自分の手元にしかない記録に頼る設計は、他人の環境にそれが無いので使えない。ログを抽出するスクリプトも、置き場所がないので使えない。過去のセッションログを読む前提も、環境によっては読むファイルそのものが存在しない。

そこで、素材の在り処だけを環境依存にして、処理の手順は共通にするという形に落としました。

素材の在り処 -- 上から順に、使えるものを使う

  1. いまの会話        どの環境にも必ずある
  2. 貼られたログ      あれば加える
  3. 過去セッション    ファイルを読める環境のみ

肝は、1だけでも記事が書けることです。長いチャット1本で作りきったプロジェクトなら、その会話が全体像そのものなので、素材が足りないと謝る必要はありません。スキル本文にも「謝らない・断らない」と書き込みました。

使ってみて分かったのは、足りないのは文体だったことです

grilling を5ラウンド回して仕様を固め、そのまま実装しました。設計から実装完了までの記録は1時間24分です。そのほとんどが問い詰めで、実装は終盤のごく一部でした。

そして、できたスキルで最初の1本を書かせてみたところ、仕様どおりには動いたものの、出てきた記事が要件定義書のような文章でした。名詞だけの見出しが並び、体言止めの箇条書きが続く。事実は正しいのに、人が書いたブログには読めないのです。

そこで文体の節を足し、質問を4つから5つに増やしました。5つ目が「文体は?」で、ゆるっと・ていねい・きっちり・実況・さくっと・ハンズオンの6種類から選びます。文末をどうするか、絵文字を使うか、箇条書きをどこまで許すかが、プリセットごとに変わる仕掛けです。この記事は「ていねい」で書いています。

投稿先の作法にも、貼ってみて初めて分かったことがありました。この記事を出している EmDash では、Markdown をテキストのまま貼ると記号がそのまま残ってしまい、描画済みの状態を貼ると見出しも引用もコードブロックも表も、そのままブロックとして入りました。mermaid は描画されなかったので、図は画像とテキストで描く方針に切り替えています。ついでに、EmDash 自体を立ち上げるときに有料プラン専用の設定を外し、セッション周りの重複エラーを直しました。

真似するなら、質問の順番だけでも持ち帰ってください

今回いちばんの持ち帰りは、grilling という道具そのものよりも「質問には順番がある」という一点でした。答えが他の未解決の質問に依存する質問は、いま聞いても意味がない。この規律を入れるだけで、対話の質がはっきり変わります。スキルを作らなくても、次のチャットから使えます。

あわせて、推奨案を必ず添えるという作法も効きました。答える側は「全部それでいい」と返せば済むので、質問が10個あっても止まりません。答えるコストが低いから最後まで走る、という設計です。私は自分のスキルの質問文にも、これをそのまま持ち込みました。

もうひとつ。使う前に想像で仕上げようとしないほうがよさそうです。文体の問題も、投稿先で記号が残る問題も、1回動かすまで気づけませんでした。作ったら早めに1本流してみて、出てきたものを見てから直す。そのほうが確実でした。

同じように自作スキルを育てている方がいたら、最初の1回で何が壊れたかをぜひ聞かせてください。私はこれから、Gemini に貼っても同じ挙動になるかを確かめるつもりです。配布物としては、そこが確かめられていないと意味がないので。
