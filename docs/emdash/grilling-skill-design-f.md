## この記事のとおりに進めると、あなたの手元に自作スキルが1枚できます

作ったのは `chat-to-article` という、AIとのチャットを素材に記事を書き起こすスキルです。実体は `SKILL.md` が1ファイル、4,000字ほど。スクリプトは1本もありません。特筆したいのは中身より作り方で、実装に入る前に **grilling**(AIに自分を容赦なく問い詰めさせる工程)を通したところ、1文字も書かないうちに設計が3回ひっくり返りました。私がスキルを自作するのは初めてではありませんでしたが、着手前に設計が崩れる経験は初めてで、これは手順として共有する価値があると思いました。

この記事は、あなたが同じことを再現するための手順書です。作るものはあなた自身のスキルで構いません。所要は、私の記録では設計から実装完了まで1時間24分でした。

```
grill-me を呼ぶ → ラウンド制で質問に答える → 合意ができる
   → SKILL.md を1枚書く → 置き場所に配置 → /コマンド で使う
```

上の1行が全体の流れです。前半3つが grilling、後半3つが実装と導入にあたります。

## 手順1 — grilling を入れて、何をするものか掴む

grilling は Matt Pocock の配布スキル集に入っています。37個あるうちの1つで、作者自身が「最も人気のあるスキル。変更を加えるときは毎回使え」と書いているものです。実体は 2,015バイトしかありません。

導入は次の1行です。

```
npx skills add mattpocock/skills
```

**確認ポイント**: 入ったら `/grill-me` が候補に出てくるかを見てください。このスキル集は37個中22個が明示呼び出し専用で、会話から勝手に発動しません。「入れたのに動かない」ではなく、そういう設計です。

中身を先に押さえておくと、答える側のコストがぐっと下がります。核はこの一文です。

> 決定事項を設計ツリーとして捉えよ。フロンティアとは、前提がすでに確定している決定の集合——つまり、まだ聞いていない答えを推測せずに、今この瞬間に聞ける質問のことである。

ふつうのAIも「確認させてください」と質問を並べますが、その中には上の答え次第で消滅する質問が混ざっています。grilling はそれを構造的に禁じます。図にするとこうです。

```
        「記事化スキルを作る」
         ├─ 素材はどこから取る？   ← 今聞ける
         ├─ 出力はどこに置く？     ← 今聞ける
         └─ 秘匿情報はどうする？   ← 今聞ける
              └─ 伏せ字の具体ルールは？  ← 「伏せる」と決まるまで聞けない
                   └─ 会社名は残す？      ← さらにその後
```

つまり、下段の質問を今されても答えようがないので、grilling は今答えられる質問だけをまとめて出してくる、ということです。

## 手順2 — 作りたいものを一言だけ言って `/grill-me` を打つ

準備はこれだけです。仕様を考えてから呼ぶ必要はありません。

```
/grill-me
```

私の場合、渡した一言は「AIとのやり取りを記事化する、というスキルを作りたいと考えています」でした。この粒度で十分です。

**詰まりやすい所**: ここで「ちゃんとした要件を書いてから呼ばなきゃ」と身構えると、grilling を使う意味が半分消えます。事実を調べるのはAI側の仕事だと明記されているスキルなので、こちらは決定だけを持てばよいのです。

> 事実を見つけるのはお前の仕事であり、断じてユーザーの仕事ではない。(中略)決定はユーザーのものである。

実際、私が「プロジェクト全体のログを素材にしたい」と答えた直後、AIは勝手に手元のログを実測してきました。プロジェクトAが9セッションで34MB、Bが1セッションで15MB、Cは0本。34MBは文脈に入りませんし、Cのようにログが1本も残っていないケースもあります。**この事実は、聞かれていたら私には答えられませんでした。**

## 手順3 — ラウンドごとに答える。迷ったら「全部推奨で」

grilling は質問に必ず推奨案を付けてきます。番号と `➡️` の行が並ぶ形式です。全部そのままでよければ「全部推奨で」の一言で次のラウンドに進みます。

| ラウンド | 決まったこと |
|---|---|
| 1 | 素材の範囲、記事の型、出力形式、秘匿情報の扱い |
| 2 | 素材の取り出し機構(仕切り直しあり) |
| 3 | 環境差の吸収、配布の入口、1ファイルに収めるか |
| 4 | 記述言語、実行時に聞く質問セット、伏せ字ルール、スキル名 |
| 5 | 記事の構成テンプレート、引用スタイル |

私は5ラウンド回しました。ここが所要時間のほとんどを占めます。

**詰まりやすい所その1 — AIが目的をすり替えてきたら、遠慮なく止めてください。** ラウンド2で私は「どのコミュニティに出しますか」と聞かれました。それらしい質問ですが、答えていて違和感がありました。止めてこう言っています。

> 私がやりたいのは、記事を作る、ということではありません。記事を作るためのスキルを作る、です。

これで決めることが2層に分かれていると分かりました。スキルの仕様(発動方法・素材の取り方・出力先)は今決めること。読者やトーンは記事ごとに変わることなので、**スキルに埋め込むべきは答えではなく「聞く仕組み」**でした。気づかずに進んでいたら、私にしか使えないスキルができていたはずです。

**詰まりやすい所その2 — 配布するなら、動く環境を先に言ってください。** 私はラウンド3の手前で「これは配布物で、Gemini で使うとプロンプト1本しか登録できない」と伝えました。ここで、スクリプトを持つ案と、私個人のダッシュボードの記録を素材にする案が同時に消えました。他人の環境にない資産には依存できないからです。

**確認ポイント**: ラウンドが進んで「フロンティアが空になりました」「これで合っているか確認させてください」と言われたら、そこが終了地点です。ここまで着手させないのが grilling の作法なので、勝手に実装が始まっていたら止めて構いません。

## 手順4 — SKILL.md を1ファイルで書く

合意ができたら実装です。ファイルは1つだけ。私の構成は次のとおりでした。

```
skills/
└─ chat-to-article/
   └─ SKILL.md      ← これ1枚で完結
skills.sh.json      ← npx skills add 用
README.md
LICENSE
```

冒頭の frontmatter に3つ書きます。

```yaml
---
name: chat-to-article
description: >-
  AIとのチャットのやり取りを素材にして、記事(Markdown)を書き起こす。
  article / blog post / writeup / 記事化 / ブログ。
  USE WHEN ユーザーが「この作業を記事にしたい」と言ったとき。
  DO NOT USE WHEN 社内報告書・議事録が目的のとき。
disable-model-invocation: true
---
```

`name` はフォルダ名と揃えます。`description` は発動判定に直結するので、**USE WHEN と DO NOT USE WHEN を両方書いてください。** 日本語で書く場合も英語キーワードを混ぜておくと判定が安定します。`disable-model-invocation: true` を付けると自動発動が切れ、`/chat-to-article` と自分で打ったときだけ動きます。会話中に「記事にすると面白いね」と言っただけで書き始められたら邪魔なので、私はこれを付けました。

本文は日本語の手順書です。**スキルの言語が出力の言語を引っ張る**ので、日本語の記事を書かせたいなら本文も日本語にしてください。私のスキルは4,000字ほどで、手元の自作スキル9個のうち7個は同じくスクリプトなしです。1ファイル・Markdownだけで足りる範囲は思っているより広いということです。

## 手順5 — 置き場所に入れて、実際に呼ぶ

置き場所はここです。

```
~/.claude/skills/<スキル名>/SKILL.md
```

置いたら呼びます。

```
/chat-to-article
```

**確認ポイント**: 候補に出てこないときは、フォルダ名と `name` が一致しているかを先に見てください。

**詰まりやすい所** — リポジトリ側とこの置き場所の二重管理になります。私は最初 `cp` で手で同期していました。GitHub に上げて `npx skills add <owner>/<repo>` で入れ直すと、この二重管理は解消します。

## 手順6 — 1回使って、出てきた不満をそのまま仕様に足す

ここを飛ばさないでください。私はこの手順で一番大きい修正が出ました。

初回実行では、スキルは仕様どおりに動きました。質問の数も、時系列をなぞらない再構成も、伏せ字の報告も、保存先を勝手に決めない点も、書いたとおりに出ました。**それでも記事は要件定義書のような文章でした。** 事実は正確なのに、人が書いたブログに読めない。仕様に「どう書くか」が一行もなかったからです。

そこで文体の節を足し、文体プリセットを6種(ゆるっと/ていねい/きっちり/実況/さくっと/ハンズオン)用意して、実行時の質問に加えました。質問は4問から5問になり、何の話か・読者・主眼・公開範囲・文体、の5つになっています。いま読んでいるこの記事はハンズオンのプリセットで書かれたものです。

同じ回で、他にも3点を仕様に昇格させました。素材が多いときの分割提案は質問を増やさず選択肢に混ぜること、伏せ字はグレーゾーンを別立てで申告すること、そして**数字は素材で裏が取れるものだけ使うこと**です。3つ目は自分に跳ね返ってきて、初回の記事に書いた「実装は10分」という体感の数字を、裏の取れる言い方に書き直しました。

投稿先の実測でも直すことが出ました。今回の投稿先は Cloudflare 製のCMSで、Markdown をテキストのまま貼ると記号がそのまま残り、描画済みの状態を貼ると見出しも引用もコードブロックもブロックとして入りました。mermaid は描画されないので、図はテキスト図解に切り替えています。

## 真似するなら、順番はこの3つです

再現の要点を絞ると、次の3つに尽きます。

1. **仕様を考えてから grilling を呼ばない。** 一言渡して問い詰めさせるほうが速いです
2. **「今決めること」と「実行時に聞くこと」を分ける。** ここを混ぜたスキルは自分専用になります
3. **1回使ってから直す。** 想像で足した仕様より、使って出た不満のほうが確実に効きます

grilling は要件定義ではありません。プロジェクト単位ではなく変更単位で、着手ボタンを押す直前に毎回挟むものです。経験のある先輩に「これ作ります」と言って15分詰められる、あの15分を構造化したもの、と考えると距離感が合います。

あなたが最初に作るなら、いま手作業で毎回やっている説明や整形を1つ選ぶのがおすすめです。私の1つ前の自作スキルも「GitHubリポジトリを初心者向けに解説する」で、会話で実際にやっていたことをそのまま手順に落としただけでした。作ってみて「ここが足りない」が出たら、その場で `SKILL.md` に足していく。それが一番早い育て方です。

もし同じ手順で作ってみて、grilling が想定外の場所で刺さった、あるいは全然かみ合わなかったという話があれば、ぜひ聞かせてください。私の次の宿題は、この1ファイル設計が Claude Code 以外でも本当に同じ挙動になるかの検証です。
