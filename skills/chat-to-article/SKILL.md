# チャットを記事にする

**目的は「作ったものを他人に届けること」**であって、やり取りの記録を残すことではない。
記事の主役は**成果物と、読者が持ち帰れる知見**である。会話は素材にすぎない。

作業の追体験を書いてはいけない。読者は他人の試行錯誤の順番に興味がない。

## 進め方

### 手順1 — 素材を集める

**上から順に、使えるものを使う。1 だけでも記事は書ける。**

1. **いまの会話** — どの環境にも必ずある。まずこれを素材とみなす
2. **ユーザーが貼った/添付したログ** — あれば加える
3. **過去のセッションログ** — **ファイルを読める環境でのみ**。ユーザーに場所を尋ねるか、
   既知の保存先を探す(例: Claude Code なら `~/.claude/projects/<プロジェクト>/*.jsonl`)。
   読めない環境ならこの手順は飛ばす。**存在を前提にしない**

> ログは大きい。数十MBに達することがあるので、**全文を読もうとしない**。
> 手順2の目次づくりで必要な箇所を特定してから、そこだけ読む。

素材が「いまの会話」だけの場合も、**謝らない・断らない**。長いチャット1本で作りきった
プロジェクトなら、その会話が全体像そのものである。

### 手順2 — 目次をつくる

素材から「**何をやったか**」を時系列で箇条書きにする。10〜30項目が目安。

このとき拾うもの:

- 作ったもの・変えたもの(成果)
- **詰まった点と、その解決**(記事の栄養はここに集中している)
- 判断が分かれた選択と、選んだ理由
- 想定と違った事実、驚き

このとき捨てるもの:

- 試して即やめたこと、単純な打ち間違い、環境構築の定型作業
- 同じことの繰り返し
- **記事の主眼に関係しない枝葉**(手順3で主眼が決まったら、もう一度捨てる)

目次はユーザーに見せなくてよい。**執筆のための作業メモ**である。

### 手順3 — 6つだけ確認する

目次ができたら、**1往復で**確認する。番号を振り、**推奨案を必ず添える**
(ユーザーが「全部それでいい」と言えるようにする)。
**Q1 は出力形式。** これは投稿先で機械的に決まるものではなく、ユーザーが選ぶ。

```
Q1 出力形式は？
   (a) HTML ファイル — ブラウザで開いて範囲コピー → CMS の本文欄に貼る。
       図は SVG 画像で入る。EmDash 等、Markdown を解釈しないエディタ向け
   (b) Markdown — そのまま貼れる投稿先(Qiita / Zenn / GitHub / note / Wiki)向け。
       図はテキスト図解か mermaid
   ➡️ <投稿先が会話から分かるなら、その投稿先プロファイルの既定を推奨。
       不明なら (b)>。投稿先は <推定した投稿先プロファイル> と想定

Q2 何を作った話にしますか？
   ➡️ <素材から推測した一行を提示する。考えさせない>

Q3 読者は誰ですか？
   (a) 一般の開発者  (b) 特定の技術コミュニティ  (c) 社内
   ➡️ <推奨>

Q4 記事の主眼は？
   (a) 成果物の紹介  (b) 詰まった所と解決  (c) 得られた学び
   ➡️ <目次で一番厚い部分から推測して推奨>

Q5 公開範囲は？
   (a) 一般公開  (b) 限定公開  (c) 社内のみ
   ➡️ 迷うなら (a)。伏せ字が最も厳しくなり、後から緩められる

Q6 文体は？
   (a) ゆるっと  (b) ていねい  (c) きっちり  (d) 実況  (e) さくっと  (f) ハンズオン
   ➡️ <Q3 の読者と、投稿先のコミュニティの空気から推奨。詳細は「文体プリセット」>
```

**7問以上にしない。** 質問が増えるほど書き始めが遠のく。
足りない情報は、書いてから直せばよい。

**素材が 1本に収まらない場合は、質問を増やさず Q2 の選択肢として出す。**
「(a) ○○の話 / (b) △△の話 / (c) 2本に分ける」の形にし、どれを勧めるかを言う。
分割の判断だけを別の質問に切り出さない。

### 手順4 — 書く

構成は下記「記事の型」に、文体は下記「文体」に従う。
**コミュニティの仲間に向けて、自分の体験を自分の言葉で話す記事**にする。
書き上げたら手順5の点検を必ず通す。

### 手順4b — タイトルを本文から作る

本文を書き終えてから、**内容を読み直してタイトル案を 3 つ**作る(先に決めない。書く前のタイトルは
仮題で、本文とずれる)。3 案は切り口を変える:

1. **結果型** — 何がどうなったか(「〜したら、〜が3回変わった」)
2. **読者の得型** — 読者が持ち帰れること(「〜で詰まる人のための〜」「〜を貼るだけで出す方法」)
3. **一言型** — 山場の一言・意外な事実(「AI の分析より人間の案が勝った」)

ルール: **文体プリセットに合わせる**(ゆるっとなら口語や絵文字可、きっちりなら体言止め可)。
**本文にある事実・数字だけを使う**。誇張しない。35 字前後、長くても 45 字。
**推奨を 1 つ選び、理由を一文添える。** 採用案を `<title>` / `<!-- title -->` / Markdown の `#` に入れ、
3 案はチャットの報告に載せる(記事本文には入れない)。ユーザーが別案を選んだら差し替える。

### 手順5 — 秘匿情報を処理する

**公開は取り消せない。書き終えたら必ず全文を点検する。**

| 既定で**伏せる** | 既定で**残す** |
|---|---|
| 個人名・メールアドレス・アカウント名 | 技術名・OSS 名・バージョン |
| 会社名・顧客名・テナント名・独自ドメイン | 公開済みリポジトリや記事の URL |
| 絶対パスのユーザー名(`/Users/taro/` → `/Users/<user>/`) | 一般的なエラーメッセージ |
| API キー・トークン・ID・内部ホスト名 | 公開ドキュメントへのリンク |
| 未公開の社内固有名詞 | 一般に知られた製品名 |

- Q5 が **(c) 社内のみ**なら伏せ字は不要。**(a) 一般公開**なら上表を厳格に適用する
- **記事の中に「※社名は伏せました」と書かない。** 伏せた事実自体が情報になる
- 置換した内容は**記事に含めず、チャットでユーザーに一覧報告する**:
  「3箇所を置換しました: 会社名→A社 / パスのユーザー名→`<user>` / メールアドレスを削除」
- **判断に迷ったら伏せる**。伏せすぎは直せるが、漏れは直せない
- **グレーゾーンは別立てで申告する。** 伏せるか残すかは全か無かではない。
  「単体では特定できないが、他の情報と組み合わさると絞り込める」ものは、
  **残したうえで理由を添えて報告し、判断をユーザーに返す**:
  「『9セッション34MB』はプロジェクト名を伏せたので特定不能と判断し残しました。
  気になるなら削れます」

### 手順6 — 出力する

- **タイトル案 3 つ(推奨付き)を、記事とは別にチャットで示す**(手順4b)。CMS のタイトル欄に貼る
  文字列として、採用案を単独の行で出す
- **保存先を必ず尋ねる。** 勝手に決めない
- **出力形式は Q1 の答えに従う**(HTML ファイル / Markdown)。投稿先プロファイルは、その形式の中での作法を決める。
  **投稿先の「貼り方」を 3〜5 行で添える**(下記「投稿先プロファイル」参照)
- ファイル書き込みができない環境では、**チャットに Markdown を丸ごと出力**する
- ファイル名は内容から決める(例: `cloudflare-transfer-cost.md`)

## 文体 — 人が書くブログとして

この記事は**コミュニティのサイトに載る、仲間に向けた投稿**である。
仕様書でも報告書でもない。**同じコミュニティの一人が、やってみたことを自分の言葉で話している**——
読んだ人がそう感じる文章にする。

- **一人称で、自分の体験として書く。**「〜を実装した。〜を採用した。」と事実を並べるのではなく、
  「最初は〜するつもりだった。ところが〜」のように、**自分が何を考え、どこで考えが変わったか**を書く
- **文末・絵文字・砕け具合は Q6 のプリセットに従う**(下記「文体プリセット」)。
  プリセットが許す範囲で、素材の会話でのユーザーの口調に寄せる。記事の中で混ぜない
- **地の文(段落)で運ぶ。** 表・箇条書き・コードブロックは、比較・手順・実際のコマンドなど
  **それが一番分かりやすい場所にだけ**使う。1記事に数箇所が目安。
  見出しの直後を箇条書きで始めない。段落を体言止めの断片で埋めない
- **見出しは文にする。**「できたもの」「学び」のような名詞ラベルではなく、
  「やってみたら設計が3回変わった」「一番効いたのは質問の順番だった」のように、
  **見出しだけ読んでも話の筋が分かる一文**にする
- **判断の理由と、そのときの気持ちを一言添える。**「意外だった」「正直ここで止まりかけた」
  「これは楽しかった」——ただし感想の羅列にはしない。事実 → 自分はどう思ったか、の順
- **読者に話しかける場面を作る。**「同じところで詰まった方は」「試すならここから」のように、
  読む人が当事者になる文を、記事に 2〜3 箇所入れる
- **結びは、読んだ人への一言で終える。** コミュニティへの呼びかけ
  (「試したら感想を聞かせてください」「うまくいかなかった例があれば知りたいです」)や、
  次に自分がやるつもりのこと。「以上」「まとめでした」で終えない
- **書き終えたら音読するつもりで通読する。** 人が話している文になっていなければ、書き直す

**避ける表現**: 「本記事では〜について述べる」「〜を実現した」「〜が可能となる」「〜を行った」
「以下に示す」「〜については後述する」。これらが出たら仕様書に戻っている合図
((c) きっちり でも、これらは使わない)。

### 文体プリセット(Q6)

上の原則は全プリセット共通。**プリセットは「どれだけ砕けるか」と「何を許すか」を変える。**
推奨は Q3 の読者から決める: 特定コミュニティなら**その場の空気**(投稿例があれば読む)、
一般の開発者向け技術メディアなら (c)、社内なら (b) か (e)。

| | 文末 | 絵文字 | 表・箇条書き | 特徴 |
|---|---|---|---|---|
| **(a) ゆるっと** | 口語。「〜なんですよ」「〜でした😇」。です・ます崩し | **多め**(見出し必須、段落は2つに1つ) | ほぼ使わない。**代わりに図解** | 独り言・脱線・オチを許す。友達に話す距離感。1段落2〜3行。図解 2〜4 枚 |
| **(b) ていねい** | です・ます | 使わない | 少し | 落ち着いたブログ。既定の中庸 |
| **(c) きっちり** | だ・である | 使わない | 使ってよい | 技術メディア(Qiita / Zenn)向け。再現性と正確さ優先。ただし仕様書調は禁止 |
| **(d) 実況** | です・ます or 口語 | 少し | ほぼ使わない | 「ここで AI がこう言ってきた→自分がこう返した」の**やり取りを多めに引用**(5箇所まで可)して、その場にいる感じを出す。時系列に見えてもよいが、山場だけを並べる |
| **(e) さくっと** | 体言止め可 | 少し | 使ってよい | 冒頭に3行の要約(TL;DR)。全体 1,000〜1,500字。SNS・社内チャット共有向け |
| **(f) ハンズオン** | です・ます。二人称「あなた」 | 使わない | 手順で使う | 読者が同じことを再現する前提。手順番号・コマンド・確認ポイントを揃える。自分の体験は「詰まりやすい所」の注釈として入れる |

**(a) ゆるっと で特に守ること** — 目標は「**読み手にすーっと入る**」こと。文字で説明しきろうとしない。

- **1段落 = 1つのこと、2〜3行まで。** 4行を超えたら段落を割る。長い説明は図解に逃がす
- **絵文字は多めに。** 見出しには**必ず1個**(先頭か末尾)、段落は**2つに1つ**を目安に末尾へ。
  飾りではなく**気持ちの代わり**に置く(「😇」= やらかし、「🔥」= 盛り上がり、「💡」= 気づき、
  「🤔」= 迷い、「🙌」= できた、「👋」= 読者への呼びかけ)。1記事で 12〜20 個
- **図解を 2〜4 枚入れる。** 仕組み・流れ・比較・ビフォーアフターは、文章で説明する前に
  下記「図解」の方式(Q1 の出力形式で決まる)で見せる。図の直後に「つまり〜ってこと」の一言を添える
- **見出しは短く**(「3回目、全部消えた 😇」)。見出しだけ拾い読みしても話が追えるように
- 「〜と思います」「〜な気がします」「〜なんですよ」のような**言い切らない文・話し言葉**を混ぜる
- 会話の引用は**短く切って**使う(1〜2行)。長い引用は読む速度を落とす
- **ただし事実の正確さと伏せ字の厳格さは緩めない。** ゆるいのは口調だけ

### 図解

**「仕組み」「流れ」「分岐」「比較」は、文章より先に図で見せる。** ふわっとした記事ほど効く。
ゆるっと・ていねい・実況・ハンズオンでは 1〜4 枚、きっちり では必要なら、さくっと では 1 枚まで。
**図の方式は Q1 の出力形式で決まる: HTML → 方式 C(+ A)、Markdown → 投稿先プロファイルの指定(A か B)。**
どの方式でも、**図の直後に必ず 1 行、言葉で要約する**。

**方式 A — テキスト図解**(どこに貼っても崩れない。EmDash など mermaid 非対応の投稿先の既定):
- **一行フロー**: `会話 💬 → 目次 📋 → 6問 ❓ → 記事 ✍️`(段落として書く。矢印は `→`)
- **段階リスト**: 番号付きリストで「上から順に使う」「ここで分岐」を示す
- **コードブロック内の簡易図**(言語指定なし): ツリーや分岐を `├─` `└─` と空白で描く。幅 40 字まで
- 比較は表(表が使えない投稿先では箇条書き)

**方式 B — mermaid**(Qiita / Zenn / GitHub など、描画できる投稿先のみ):
- fenced code block(```` ```mermaid ````)。1枚の図に**ノードは 7 個まで**。ラベルは短い日本語
- 使い分け: 流れ・因果 → `flowchart LR/TD`、時系列 → `timeline`、やり取り → `sequenceDiagram`
- ラベル内で `"` `()` `[]` `{}` `|` を避ける(パースが壊れる)

**方式 C — SVG 画像(data URI)**(HTML で出力する投稿先 = EmDash の既定):
- 図を **SVG で手書き**し、`<img src="data:image/svg+xml;utf8,...">` として HTML に埋め込む。
  `<svg>` を直接置かない(貼り付け時に捨てられる)。`<img>` の data URI は**貼り付け・公開の両方で残る**(実測済み)
- SVG は **箱(rect rx=8)+ 短いラベル(text)+ 矢印(line / path)** だけで組む。
  `viewBox="0 0 W H"`、幅は 520〜640、箱は 7 個まで、1 行のラベルは 8 字まで。
  文字は `font-family="sans-serif" font-size="14" text-anchor="middle"`。色は 2 色(箱の塗り 1 色 + 線 1 色)
- data URI 化: SVG を 1 行にし、`#` → `%23`、`<` → `%3C`、`>` → `%3E`、`"` → `'` に置換して
  `src="data:image/svg+xml;utf8,…"` に入れる。`<img>` には `alt` と `style="max-width:100%"` を付ける
- 図が複雑になるなら(木構造 3 段以上、ノード 8 個以上)、方式 A に落とす。**崩れた図は無い図より悪い**

### 投稿先プロファイル

投稿先は**会話から推定**し(「コミュニティのサイト」「Qiita に」など)、Q1 の推奨文に
「投稿先は ○○ と想定」と添えて確認する。**投稿先の専用質問は増やさない。** 不明なら「汎用」。
表の「出力形式」列は **Q1 の推奨値**であり、ユーザーが Q1 で逆を選んだらそちらに従う
(例: EmDash で Markdown を選んだら、Markdown を出して「描画された見た目をコピーして貼る」と案内する。
Qiita で HTML を選んだら、HTML を出したうえで Qiita は HTML を貼れないことを一言添える)。

| プロファイル | 出力形式 | タイトル | 本文の開始 | 使ってよい要素 | 使わない | 図解 |
|---|---|---|---|---|---|---|
| **EmDash**(Cloudflare 製 CMS) | **HTML ファイル 1 本**(下記) | `<title>` と本文冒頭の `<!-- title -->` コメント。本文に `<h1>` は置かない | `<h2>` から | `h2〜h4`・`p`・`ul/ol`・`blockquote`・`pre><code class="language-xx"`・`table`・`strong/em/code/a`・`hr`・`img`(data URI か外部 URL) | **mermaid・`<svg>` 直置き・脚注・`<h1>`・`<script>`・`<style>` 以外の装飾タグ** | 方式 C(+ 方式 A) |
| **Qiita / Zenn** | Markdown | `#` を本文先頭に | `##` から | 汎用 Markdown + mermaid・画像・脚注 | HTML タグ | 方式 B |
| **note** | Markdown | 本文先頭に `#` | `##` から | 見出し・段落・引用・リスト・太字 | 表・コードブロック(引用で代用)・mermaid | 方式 A(一行フローのみ) |
| **社内 Wiki / Teams** | Markdown | `#` | `##` から | 汎用 Markdown 一式 | mermaid(描画不明) | 方式 A |
| **汎用**(不明) | Markdown | `#` | `##` から | 汎用 Markdown 一式 | mermaid・HTML | 方式 A |

**EmDash の出力(HTML ファイル)**: EmDash のエディタは Markdown の記号を解釈しないが、
**ブラウザで描画された HTML を範囲選択コピーして貼ると、見出し・引用・コードブロック(言語ラベル付き)・
表・data URI 画像・絵文字がすべてブロックとして入り、公開後もテーマの装飾で表示される**(実測済み)。
そこで EmDash 向けは、記事を**自己完結の HTML ファイル 1 本**として出す:

```html
<!doctype html><html lang="ja"><head><meta charset="utf-8">
<title>記事タイトル</title>
<style>body{font-family:sans-serif;max-width:720px;margin:2rem auto;line-height:1.8}
pre{background:#f4f4f4;padding:1em;overflow:auto}table{border-collapse:collapse}
td,th{border:1px solid #bbb;padding:4px 10px}img{max-width:100%}</style></head>
<body><article>
<!-- title: 記事タイトル -->
<h2>…</h2> …
</article></body></html>
```

- `<style>` は**閲覧用**(貼り付け時には捨てられ、EmDash 側のテーマが当たる)。凝らない
- コードブロックは `<pre><code class="language-bash">` のように**言語を必ず付ける**(EmDash が言語ラベルにする)。
  `<` `>` `&` は実体参照(`&lt;` `&gt;` `&amp;`)に
- 図は方式 C(`<img src="data:image/svg+xml;utf8,…">`)。`<svg>` の直置きは貼り付けで消える
- Markdown を書けない環境ではない(Gemini など)場合も、**HTML をコードブロックで出す**。ユーザーはそれを
  `.html` として保存してブラウザで開く(Gemini の Canvas プレビューでも可)
- 本文には `<h1>` を置かない(タイトルは CMS 側)。Excerpt(抜粋)欄には本文を入れない

**EmDash の貼り方(手順6で必ず案内する)**:
1. HTML ファイルをブラウザで開く(ダブルクリックで可)
2. ページ上で **Ctrl+A → Ctrl+C**(描画された見た目ごとコピーされる)
3. EmDash の **投稿 → 新規作成 → 本文欄をクリック → Ctrl+V**
4. タイトルは CMS のタイトル欄に入力。先頭の `<!-- title -->` コメントは貼り付けで消えるので気にしない
5. 公開前に「保存」、公開時は「公開」ボタン(公開済み投稿の更新も「公開」)

## 記事の型

背骨は 1 本。**主眼によって、どこを厚くするかだけを変える。**
これは**執筆のための骨組み**であって、見出しの文言ではない(見出しは文にする。上記「文体」参照)。

```
① タイトル       本文を書いた後に手順4b で 3 案作る。成果物名 +「読者にとっての嬉しさ」。誇張しない
② 書き出し (3〜5行)  何をしようとして、何ができたか。★結論を先に出すが、
                   「なぜ自分がこれをやろうと思ったか」の一行を必ず入れる
③ 何ができたか   出力例・画面・使用感。読者が「欲しい」「自分もやりたい」と思う場所
④ どう作ったか / どこで詰まったか
⑤ やってみて分かったこと・真似するなら
⑥ 結び + リンク  読者への一言で終える
```

| 主眼 | 厚くする節 | 書き方 |
|---|---|---|
| 成果物の紹介 | **③** | 使用例を具体的に。読者が真似できる形で |
| 詰まった所と解決 | **④** | **問題 → 仮説 → 検証 → 解決**の順。原因が分かった瞬間の驚きや安堵を書く |
| 得られた学び | **⑤** | 一般化して書く。この案件でしか通じない話にしない。ただし語り口は自分の体験のまま |

### 会話の引用

**原則は再構成。** 生ログを貼らない。読者は他人の会話を読みたいわけではない。

ただし**山場だけは引用ブロックで見せる**。AI がこう答えた、という瞬間には固有の説得力がある。
1記事に 1〜3箇所まで。引用するなら、その前後に「なぜこれが効いたか」を必ず添える。

### 分量

- **成果物 1つ = 記事 1本**が既定
- 素材が多く 1本に収まらない場合は、**テーマで分割することを提案する**
  (「この内容は『導入編』と『つまずき編』の 2本に分けたほうが読まれます」)。
  提案は手順3の **Q2 の選択肢として**出す。専用の質問を増やさない
- 目安は 2,000〜5,000字。長さより、**削ったかどうか**が質を決める

## 書き方の規範

- **結論を先に。** 導入で「何を作って、何が良かったか」を言い切る
- **読者が再現できる粒度で書く。** コマンド・設定値・バージョンは具体的に
- **失敗を隠さない。** 詰まった話が記事の価値。ただし失敗の羅列にはしない
- **数字と固有名詞を入れる。**「速くなった」ではなく「12秒 → 1.4秒」
- **ただし、書ける数字は素材で裏が取れるものだけ。** 素材にない数値を体感で補わない。
  裏が取れないが書きたいなら、**曖昧なまま書く**(「1時間半」ではなく「一晩」)か、
  ユーザーに確認する。**捏造された数字は記事全体の信頼を落とす**
- **見出しだけ読んでも筋が通る**ようにする
- **具体性は散文の中に埋める。** 数字・コマンド・設定値は必要だが、それを表に並べて終わりにしない。
  「なぜその値になったか」を地の文で語る
- **AI の宣伝をしない。**「AI はすごい」は記事の中身ではない

## やってはいけないこと

- 会話の時系列をそのままなぞる(**最も多い失敗**)
- 素材にない事実を補って書く。分からないことは書かない
- 「〜してみました」「いかがでしたか」のような中身のない定型句
- **仕様書・報告書の文体で書く**(名詞ラベルの見出し、体言止めの箇条書きの連打、
  「〜を実現した」「〜が可能となる」)。ブログの文体は上記「文体」参照
- 成果を誇張する。動いていないものを動いたように書く
- 秘匿情報の点検(手順5)を飛ばす
- 保存先を勝手に決める
- 7問以上の質問で書き始めを遅らせる
